# Elasticsearch 与 Milvus：给 RAG 打好检索地基

这是一份以 RAG 为目标的学习专栏。

先想清楚一个问题：问大模型"我们公司去年的退款政策是什么"，它要么答不上来（训练数据里没有），要么一本正经地编一个（幻觉）。RAG 的思路很直接——生成之前先检索，把相关资料塞进上下文，让它照着答。但这里有个容易被忽略的事实：**RAG 答得好不好，瓶颈通常不在生成，而在检索。** 模型拿到的是垃圾资料，再强的模型也只能答出垃圾。

而"检索"这件事，在 RAG 里有两条路：

- **关键词检索**：用户搜"退款"，就得精确匹配到含"退款"两个字的内容。快、准、可解释，但搜不到"意思相近却用词不同"的内容。
- **向量检索**：把文本压成一串数字（embedding），"如何退货"和"退款流程"在向量空间里距离很近，能搜到。但它对专有名词、型号、错误码这类**必须一字不差**的内容反而不可靠。

两条路各有盲区，所以成熟的 RAG 系统通常是两条都要（混合检索）。ES 守第一条路，Milvus 守第二条路。这份专栏就把这两块地基打牢，最后用一个 RAG 项目把它们拧在一起。

学法遵循一条原则：**先会用，再懂原理。** 专栏一、二解决"会用"，用得过程中概念自然带出来；专栏三集中往深挖一层，回答"凭什么快、凭什么省、挂了怎么办"；专栏四是落地项目。

> 说明：配图统一放在各专栏目录的 `assets/` 下，生成脚本在 `gen_charts/`。文中版本敏感的细节（客户端 API、默认参数）以写作时的主流版本为准，动手前建议对照官方文档核一遍。

## 专栏五：动手实验，把机制摸出温度

前四个专栏是"看懂"，这个专栏是"摸过"。读一百遍"segment 不可变"，不如亲手删一万条数据，再看一眼磁盘占用纹丝不动。17 个实验共用一套钉死版本的 Docker 环境（ES 8.11.4 + Milvus v2.4.4，含 Kibana/attu/MinIO 控制台），从热身（API 全景、磁盘眼见为实、图形界面）到核心概念（refresh、分词、动态映射、BM25、深分页、ANN 权衡、一致性、标量过滤），最后合龙成一次真正的混合检索。详见[专栏五 README](专栏五-动手实验/README.md)。

## 贯穿全程的一套权衡意识

学检索技术，脑子里始终摆着这个三角，很多"最佳实践"其实就是在三角里选位置：

- **召回率**：该找到的有没有找到
- **延迟**：用户等多久
- **资源**：内存和磁盘花多少

HNSW 的 ef 调大，召回上去了、延迟也上去了；PQ 量化省了内存、召回掉了一截；ES 的 refresh_interval 调大，写入吞吐上去了、可见性变慢了。没有免费午餐，只有清楚自己业务在哪条边上的取舍。

第二个反复出现的权衡是**关键词 vs 语义 vs 混合**：精确词重要（错误码、型号、法条编号）就偏向 BM25；口语化提问多就偏向向量；大多数真实场景落在中间，这就是为什么两个都要学。

## 刻意没讲的内容

有一块内容这份专栏刻意没收进来：**ES 的集群运维**——扩容缩容、快照备份恢复、滚动重启、机架感知这些。不是不重要，而是这份专栏的目标是 RAG 检索，运维是另一个战场，混进来会稀释主线。真到了要管生产集群的那天，再按需单独立一篇补上。

## 怎么读

如果 ES 和 Milvus 都没碰过，按顺序来：专栏一、二边读边动手，每篇的命令和代码都自己敲一遍，能独立跑起来之后进专栏三补原理，最后用专栏四收口。专栏五的实验随时可以穿插进来——每篇实验都标了对应正文，读到哪篇就做哪个实验，机制看两遍不如手跑一遍。

如果急着出 RAG 原型，也可以先只读专栏一、二的前五篇，直接跳到专栏四建起来，再回头补齐剩下的——工程上这完全成立，原理篇什么时候补都不晚，但没有地基的楼 sooner or later 会以线上事故的形式提醒你。

最后说清一个背景：这份专栏默认你有扎实的后端经验（MySQL、Redis、Kafka 级别），所以原理篇会大量用这些旧知识做对照——但每个对照都会点出"哪里像、哪里本质不同"，因为似是而非的类比是理解分布式系统最大的坑。
