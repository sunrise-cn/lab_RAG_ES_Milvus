# 00 总纲：一张地图看完全部四个专栏

这份笔记的定位：复习地图。它不复述原文细节，只干两件事——**把每个核心概念钉在知识体系里的坐标上**，以及**讲清概念与概念之间的联系**。细节、命令、代码回到四个专栏原文里查（每节都标了指针）。

## 一、全局地图：从一条慢 SQL 到一条 RAG 链路

四个专栏其实只回答了一个问题：**怎么让"生成之前先检索"这一步又快又全又准**。

```
                    ┌──────────── 文档库（source of truth）────────────┐
                    │  知识库是活的：每周改、每月调 → 增量更新 + 双写一致性 │
                    └──────────────────────┬──────────────────────────┘
                                           │ 文档变更
                                           ▼
                              ① 切分 chunking（专栏四·01）
                                 决定"数据表示"，检索质量的天花板
                                 chunk = text + doc_id/title_path/chunk_index
                                           │
                    ┌──────────────────────┼──────────────────────┐
                    ▼                      ▼                       ▼
        ②a 关键词检索（ES）      ②b 向量检索（Milvus）      （双路并发）
           BM25 打分              ANN（HNSW 默认）
           管"一字不差"           管"意思相近"
           倒排索引               embedding + 近邻图
        （专栏一、专栏三ES篇）  （专栏二、专栏三Milvus篇）
                    └──────────────────────┬──────────────────────┘
                                           ▼
                              ③ 合并：RRF 倒数排名融合（专栏四·02）
                                 分数刻度不同 → 只用排名：1/(k+rank)
                                           ▼
                              ④ 精排：cross-encoder rerank（专栏四·03）
                                 双塔管召回（快、可预计算），交叉编码管精排（准、不可预计算）
                                           ▼
                              ⑤ 喂给 LLM 的 top 3~5 条 chunk
                                           ▼
                                    生成答案（本专栏之外）

        横切两条线：
        ⑥ 评估（专栏四·04）：recall@k / MRR / RAGAS——所有调参共同的裁判
        ⑦ 工程化（专栏四·05）：增量更新、双写最终一致、降级兜底、监控
```

读这张地图的三个要点：

1. **两条腿是互补不是替代**。关键词检索的工作前提是"query 和 doc 至少共享一个词"——用户嘴里的词和文档里的词永远对不上时（语义鸿沟），它结构性失明；向量检索把"意思"压成数字，恰恰在错误码、型号、法条编号这类**必须一字不差**的地方失明。两条路各有盲区，所以都要。（专栏二·01）
2. **检索质量的瓶颈常常不在索引算法，而在更上游**。chunk 切得不对，HNSW 和 BM25 都是在错误的表示上做优化（专栏四·01）；召回里本来没有正确答案，rerank 排得再精也没用（专栏四·03）。排查检索问题永远从上游往下游走。
3. **ES 和 Milvus 是同一件事的两种物理实现**。都回答"从一堆数据里找出和查询最相关的 top-k"，只是一个用倒排索引+词频统计，一个用向量空间+近邻图；一个有"近实时"的写入语义，一个有"按请求调一致性"的读取语义。专栏三存在的意义就是把这两套内部世界分别拆开。

## 二、两个贯穿始终的权衡

### 三角：召回率 × 延迟 × 资源

原文反复使用的坐标系。几乎所有"最佳实践"都是在这三条边之间选位置：

| 旋钮 | 在哪个边上加价 | 买回了什么 |
|------|--------------|-----------|
| HNSW 的 `ef` / IVF 的 `nprobe` 调大 | 延迟 ↑ | 召回率 ↑ |
| PQ/SQ 量化 | 召回率 ↓（SQ 几乎无损） | 内存 ↓↓ |
| `refresh_interval` 调大 | 可见性变慢 | 写入吞吐 ↑ |
| DiskANN（向量下盘） | 延迟 ↑（毫秒级） | 内存 ↓↓ |
| `shard_size` 调大（terms 聚合） | 网络/归并开销 ↑ | 聚合精度 ↑ |
| DFS_QUERY_THEN_FETCH | 多一轮 RTT | 分数跨分片可比 |
| overlap 留大 | 存储/索引膨胀 10~20% | 边界内容不丢 |

没有免费的午餐。调参之前先问：我的业务卡在三角的哪条边上？

### 关键词 vs 语义 vs 混合

精确词重要（错误码、型号、法条编号）→ 偏 BM25；口语化提问多 → 偏向量；大多数真实场景落在中间 → 混合检索，RRF 合并，rerank 收口。

## 三、映射矩阵 1：ES ↔ MySQL

ES 概念的学习主线就是"拿 MySQL 对照，但每个对照都要点破哪里不一样"：

| ES | 像 MySQL 的 | 关键差异（必须记住的） |
|----|------------|----------------------|
| index | 表 | **单词陷阱**：MySQL 的 index 是加速结构，ES 的 index 是装数据的容器（≈表）；倒排索引藏在 shard 内部，你碰不到。7.x 起按 index ≈ 表记 |
| document | 行 | 自由 JSON 树，无 schema 约束；同 `_id` 再写一次是**整篇覆盖**不是报错 |
| mapping | 列定义 | 默认动态映射"先插数后猜类型"；**字段类型不可变**，错了只能 reindex |
| shard | 分库分表的分片 | 路由公式同款 `hash(_id) % N`，但原生内置路由+归并；**主分片数建后不可改**，副本数随时可调 |
| replica | 从库 | 动机是**高可用+查询吞吐**，没有"读写分离"决策；写永远走主分片、同步复制到副本，副本站在写入关键路径上 |
| refresh 1 秒 | —（无对应物） | 写入成功 ≠ 立即可搜；可见性门槛是 page cache 不是落盘 |
| 无跨文档事务 | 事务 | 单文档原子，多文档靠 bulk/上游保证；所以主数据留在 MySQL |

## 四、映射矩阵 2：Milvus ↔ 旧知识

| Milvus | 像什么 | 关键差异 |
|--------|--------|---------|
| collection / entity / field | 表 / 行 / 列 | 整张表**围绕向量字段组织**：先定向量怎么检索，再补标量字段 |
| log broker（写入第一站） | Kafka | 像：分区、顺序追加、可重放。**本质不同：消息就是数据本身**——对象存储上还没有的东西只存在于这条日志里。Kafka 丢消息通常可容忍，这里丢的是数据 |
| 一致性级别（四档） | —（无对应物） | MySQL 里"节点看到的数据"就是全部；存算分离里每个查询节点对世界的认知是一条**可以暂停、可以追赶的时间线**，所以一致性变成按请求指定的参数 |
| HNSW 多层图 | Redis 跳表 | 共享"高层稀疏、底层稠密"的形。**本质不同：跳表索引有序链表，O(log N) 有数学保证；HNSW 索引近邻图，贪心无全局保证，对数复杂度靠图质量撑着** |
| partition | MySQL 分区表 | 形似，动机不同：MySQL 为**管理**大表（备份、删历史），Milvus 为**检索裁剪**和逻辑隔离 |
| auto_id 主键 | 自增主键 | Milvus **不拦重复主键**（同主键 insert 出多条，不报错）；幂等要靠自己设计业务主键 + upsert |
| growing segment | —（无对应物） | ES 的近实时靠 refresh 造段；Milvus 把这一步做没了——增量数据靠订阅日志立即可查 |
| 向量索引 | B+ 树索引 | B+ 树精确（可证明的剪枝）；向量索引**有损**（高维无全序，只能 ANN），多一个 MySQL 里不存在的指标：召回率 |

## 五、映射矩阵 3：ES ↔ Milvus 横向对照

同一个问题的两套答案：

| 维度 | Elasticsearch | Milvus |
|------|--------------|--------|
| 检索原理 | 倒排索引 + BM25（词频统计） | 向量空间 + ANN（距离几何） |
| 数据组织 | 文档 → 分词 → 词典/posting list | 向量 → 近邻图 / 聚类桶 |
| 写入可见性 | 近实时（refresh 默认 1s） | growing segment 立即可查；可见范围由一致性级别决定 |
| 持久性兜底 | translog（WAL，对照 redo log） | log broker（消息即数据） |
| 分布式归并 | query then fetch；**分数不可比**（统计量分片本地）→ 需要 DFS 填坑 | 多路归并；**距离全局可比**，天然无此坑 |
| 过滤 | bool filter → bitmap 缓存，与算分解耦 | 表达式 → bitset，segment 内下推；向量索引不感知标量 |
| 存储哲学 | 追加式（segment 不可变 + merge），LSM 家族 | 存算分离（对象存储为真相，计算节点无状态） |
| 扩容 | 加节点；主分片数不可改，扩容量靠 reindex | 加节点；数据在共享存储，扩缩容不搬家 |
| 一致性 | 近实时是固定属性 | Strong / Bounded / Session / Eventually 四档可调 |
| 适用 | 关键词检索、复杂过滤、聚合分析、混合检索的 BM25 半边 | 大规模向量检索、量化/磁盘索引、独立重负载隔离 |

## 六、反复出现的同一批思想（跨专栏的"老朋友"）

这套专栏最值钱的部分之一：同一个思想在 ES 和 Milvus 里各出现一次，认出来它们，知识就减半。

1. **WAL（先记便宜的账，贵的动作推迟批量做）**：ES 的 translog 之于 segment；Milvus 的 log broker 之于 sealed segment。崩溃恢复都是重放日志。（专栏三·02 / 专栏三·06）
2. **不可变 + 标记删除 + 后台合并**：ES segment 的 `.del` 位图 + merge；Milvus sealed segment 的 tombstone + compaction；HNSW 的删除标记。三个地方同一个玩法，代价都是"空间迟些回收、写多有后台 IO"。（专栏三·02 / 05 / 06）
3. **批量摊销固定开销**：ES bulk（一次往返摊给千条）、embedding 批量推理、Kafka producer 攒批——同一个思想：把每条消息固定的过路费摊到一批上。（专栏一·07 / 专栏二·04）
4. **有损换资源**：ANN 用召回率换速度；PQ 用召回换内存；cardinality 用精确度换内存；terms 聚合用精确度换延迟。都是"接受一个可度量的损失，换一个数量级的收益"。（专栏二·05 / 专栏三·05 / 专栏一·06）
5. **局部 top N + 全局归并**：ES query then fetch、Milvus 多路归并、分库分表跨库 order by limit，是同一个分布式原语。（专栏三·03 / 07）
6. **最终一致 + 异步补偿，不上分布式事务**：MySQL+Redis 双写的老解法（重试队列 + 对账），在 ES+Milvus 双写上原样复用。检索场景比交易场景宽容：不一致的代价是旧文档，不是资损。（专栏四·05）
7. **幂等是重试的前提**：先删后插天然幂等；Milvus 业务主键 + upsert。凡是"失败重试"的设计，先确认动作幂等。（专栏四·05 / 专栏二·03）
