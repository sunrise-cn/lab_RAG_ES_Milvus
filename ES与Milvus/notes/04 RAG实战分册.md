# 04 RAG 实战分册

对应专栏四 5 篇。这是把两块地基拧成一条链路的部分：**切分（表示）→ 双路召回+RRF（合并）→ rerank（精排）→ 评估（裁判）→ 工程化（活在生产）**。

## 1. 文档切分：决定天花板的一步

**为什么切分比索引算法还重要**：倒排、HNSW、IVF 讲的是"在已有的数据表示上怎么查得快查得全"；切分决定的是**表示本身对不对**。就像 MySQL 里把十条记录揉成一个 BLOB 塞进一列，索引再精妙查询也是废的。

核心矛盾一句话：**chunk 既要语义完整，又要语义单一。**

- **切太大 → 语义稀释**：2000 字混三个主题，向量是三个主题的平均位置，"退款"查询相似度不上不下；BM25 也被长度归一惩罚。
- **切太小 → 上下文碎**："详见附录三"向量语义约等于零，检索生成两头不讨好；BM25 侧词太少没区分度。

经验起点：中文 300~800 字 / 256~512 token——是起点不是结论，**每次改切分策略都要能用评测集量化**（第四节的闭环）。

三种切法：

1. **固定长度**：十行代码，但一刀切不管句子死活（关键句横在边界上两头残缺）。适合无结构文本（聊天记录、工单）和天然长度均匀的内容。
2. **按结构切**（Markdown 标题等）：顺着作者的语义边界走，但会遇"标题块太长/太碎"两个新问题——实践中是**以结构为首选边界+长度约束兜底**。
3. **递归切分**（RecursiveCharacterTextSplitter）：**默认从它开始**。分隔符按优先级降级（`\n\n`→`\n`→`。`→空格→单字符），切不动就降一级，碎块低于 min 就合并相邻块。结构清晰按结构切、没结构退到句子、硬切永远排最后——在两种数据上自动滑动，犯不了大错。

**overlap 留不留**（判断框架，不是标准答案）：给边界质量买的保险，切得越准保费越不值。硬切多 → 留 10~20%（或 1~2 句）；按结构切 → 0~5% 甚至不留。代价：存储索引膨胀一两成 + 两路召回重复命中要去重。

**chunk 元数据和正文一样重要**，四个必带字段：

| 字段 | 干什么 |
|------|--------|
| doc_id | 溯源依据 + 增量更新的删除/替换主键（第五节主角） |
| title_path | 拼进 embedding 输入=免费语义锚点（"退款""时效"恰是查询高频词），两路检索都涨；拼给 LLM 帮理解出处 |
| chunk_index | 命中后取前后邻居（答案是"如上一段所述"时必需） |
| 权限/租户标签 | ES filter、Milvus 标量过滤的隔离开关——切分时不带，事后补就是全量重建 |

（原文：专栏四·01）

## 2. BM25 讲透 + 混合检索合并

### BM25：三处修正，每处解决一个具体问题

**TF-IDF 的两个直觉**：TF"出现越多越相关"——方向对但线性外推翻车（第 10 次出现不比第 2 次多说明什么，高频被系统性高估）；IDF"稀有词值钱"——至今成立，是倒排大厦地基。

**BM25 三处修正**（公式不用背，每项说得出解决什么）：

1. **词频饱和（k1=1.2）**：TF 改造成分式，词频增大趋近 k1+1 不再无限涨；k1=0 则词频完全不起作用。
2. **文档长度归一（b=0.75）**：`|D|/avgdl` 惩罚长文档——同样 3 次"退款"，100 字短文是"就讲这个"，万字长文是顺带提。b=0 不看长度，b=1 严格拉平。（chunk 切太大被罚，罚的就是这里）
3. **IDF 平滑**：经典 IDF 在词出现在过半文档时产生负分（倒扣）；BM25 改成永远非负——常见词不帮忙可以，帮倒忙说不过去。

ES 的 `_score` 默认就是 BM25（k1=1.2、b=0.75，mapping 的 similarity 可调）。**它是依赖全库统计量（N、avgdl、每个词的 n）的相对量**——记住这点，它是下一节所有坑的根源。

### 两路结果怎么合并：分数不可比

BM25 的 3.5 分和余弦的 0.85 为什么不能直接比？BM25 分数**无界**且依赖全库统计量——换个库、库平均长度变了，同一篇文档分数就变；余弦**有界**（0~1）但 0.85 算高算低取决于模型和语料，无绝对含义。**一个相对量 + 一个伪绝对量，直接比大小没有意义。**

归一化（min-max 拉到 0~1 再加权）的两个坑：

1. **刻度随召回集漂移**：本次 top 10 个个高分时，最差的也被拉接近 1；分数平平时第一名被拉满到 1——每次查询间两路的权重比例实际在漂移。
2. **离群值敏感**：一路出一个超高分离群点，这一路全被压扁。

**RRF（倒数排名融合）**：分数不可比，排名可比。`RRF(d) = Σ 1/(k + rank_r(d))`，k 通常 60。整个计算不出现任何一路的原始分数，三个坑全绕开。k=60 的含义：**有意压低排名的权威性**——第 1 名比第 2 名贡献只多不到 2%，它要的是"两路都说你靠前"的文档，不是"某一路说你第一"的文档。要偏心就加权（精确词重要加 BM25，口语化多加向量，从 1:1 起步按评测调）。ES 8.14 起内置 RRF；跨 ES+Milvus 才需要自己实现。

### 选型：什么时候单 ES 就够

ES 8.x 自带 `dense_vector` + HNSW kNN + RRF，单 ES 能闭环。四个维度算账：

1. **向量规模**（第一道分水岭）：百万级以内单 ES 够（100万×768维≈3GB）；千万级起 ES 成本曲线变陡（向量索引压在 JVM heap 上，heap 大伤 GC；segment merge 时 HNSW 跟着重算）。
2. **索引与压缩手段**：ES 的 kNN 只有 HNSW（+暴力扫），没有低配选项；Milvus 有 IVF/DiskANN/GPU 索引 + PQ/SQ 量化 + mmap 下盘——内存放不下时"能不能量化"是做不做得到的问题。
3. **标量过滤深度**（这项偏袒 ES）：ES 的 bool filter 生态成熟；两边过滤实现路径不同（ES kNN 过滤在候选收集阶段、命中比例低时凑不满 k；Milvus 下推到 segment 层更彻底但表达式能力弱）——过滤重的场景两边都要实测。
4. **团队现状**：已有成熟 ES 集群顺手加字段 vs 引入新组件的运维/监控/一致性成本；向量检索 QPS 上去吃紧 ES 时，独立出去反而是隔离风险。

**判断：百万向量以内+过滤常规+已有 ES → 单 ES 别犹豫；上千万+要量化下盘+检索是独立重负载 → 引入 Milvus**。和当年"缓存从 MySQL 内存表挪到 Redis"是同一道题。（原文：专栏四·02）

## 3. Rerank 精排：召回之后谁来定最后几条

**为什么不能全塞给 LLM**：成本是一方面，更隐蔽的是**噪声稀释注意力**——10 条混 3 条不相关，答案质量常比只给 5 条精准的更差。合并后取 20 条左右，挑 3~5 条。

**为什么现有排序手段有天花板——双塔（bi-encoder）的结构局限**：embedding 检索里，文档向量是**离线预计算**的（一百万篇各自编码建好 ANN 索引，在线只算一次 query 向量）——这是毫秒级查询的前提。代价：文档编码时**看不到 query**，query 编码时也看不到文档，两段文本零交互，全部交互压缩成最后一次点积。**表示是静态的、与 query 无关的**，而"相不相关"本质上取决于 query 问了什么。

**cross-encoder 把交互做足**：`[CLS] query [SEP] 文档` 拼成一个序列整体过 transformer，query 的每个词都能 attend 文档的每个词，输出相关性分数。判断质量明显优于双塔，但**每对 (query, 文档) 都要跑一次完整前向，没有任何东西可预计算**——一百万篇的库一次查询就是一百万次前向，几小时。

所以是分工不是替代（对照：简历初筛 vs 面试官面谈）：

> **召回用双塔**：快、可预计算、配 ANN，从一百万捞 top 100~1000，要快要全。
> **精排用 cross-encoder**：慢、准，只面对 20 条，要准。

链路是漏斗：**两路召回各 top 10~20 → RRF 合并 top 20 → cross-encoder 精排 top 5 → 喂 LLM**。

一个顺手红利：**rerank 解决了分数量纲问题**——RRF 之后每条候选的分数出自同一个 cross-encoder 对着同一个 query，量纲天然统一。RRF 管"公平凑齐候选"，rerank 管"最终座次"，各管一段。

工程要点：bge-reranker 系列 + `CrossEncoder` 十几行接上；**位置在 RRF 之后**；延迟进 P99 预算（GPU 几十毫秒/CPU 几百毫秒，吃紧先砍候选数再换小模型）；吞吐靠批量 predict；`max_length=512` 会截断长 chunk——切分质量在下游收账；**分数不跨 query 比较**（要过滤用相对规则，如"不低于第一名 60%"）。

**rerank 救不了烂召回**：cross-encoder 只能对送进来的候选排序，正确答案不在候选里，它只是把 20 条错误内容排了座次（对照：ORDER BY 管排序不管行集对不对）。排查顺序：先看正确答案在不在合并 top 20 → **不在 = 召回的病**（调 chunk、换 embedding、调 RRF 权重、补同义词），**在但排十几名 = rerank 的主场**。（原文：专栏四·03）

## 4. 检索效果评估：没有度量就没有优化

### 三个指标各问什么

| 指标 | 问什么 | 怎么算 |
|------|--------|--------|
| recall@k | **该找到的找到没有** | top k 中相关文档数 / 全部相关文档数 |
| hit rate@k | LLM 至少看到一条对的没有 | top k 含≥1条相关即命中，算比例（单标注时=recall） |
| MRR | 对的排得多靠前 | 第一个相关结果排位的倒数取平均 |

**RAG 优先 recall@k**：top 5 后面还站着 rerank 和 LLM，排序粗糙它们兜得住（第 3 名有机会被顶到第 1）；top 5 之外的正确答案谁也救不回来——rerank 见不到它，LLM 拿不到它就硬编。**漏召回不可修复，排序粗糙可修复**。MRR 那种"第一名必须对"的执念适合搜索框下拉联想。

### 评测集三步建

1. **query 来源**：真实用户日志最值钱（口语、用词习惯都在里面）；冷启动用 LLM 读 chunk 生成问题铺量，但必须人工改写——**LLM 生成的问题倾向复述文档原话**（"几个自然日内可申请退款"），而真实用户问"过了一个星期还能退吗"。
2. **标注**：分歧正常，相关性本来就主观；定一条标准写下来——**"这条 chunk 单独拿出来，能不能直接回答这个 query"**，能算相关，沾边不算。标准比人多少更重要。
3. **规模维护**：50~200 条起步；线上 badcase 脱敏回流，它就是检索界的**单元测试+回归测试集**。

### RAGAS：端到端那一层

检索层指标全绿、答案照样翻车（rerank 排错、prompt 差、LLM 理解歪）——所以要 LLM-as-judge 层，常用 RAGAS：

- **忠实度 faithfulness**（对抗幻觉核心）：答案拆成论断，逐条核对能否从检索内容推出，被支持占比。
- **答案相关性**：从答案**反向生成问题**，算与原问题的向量相似度——答非所问会跑偏。
- **上下文召回率/精确率**：自动化版本的 recall/precision，靠 LLM 裁判判断，省人力但引入裁判不确定性。

分工：**检索指标定位层级，端到端指标看效果**——recall 掉了调检索侧（chunk/权重/embedding），recall 没动但忠实度掉了查生成侧（prompt/模型）。LLM-as-judge 的局限：打分有随机性（多评取平均）、要花钱（离线抽样跑非在线全量）、换裁判=换尺子（历史数字重跑）。

### 闭环

每次改动跑一遍评测集，存数字、对比、变好的合入变差的回滚。攒下的数字还是向团队证明优化价值的证据（"recall@5 从 0.71 到 0.74"比"感觉好点了"有说服力）。（原文：专栏四·04）

## 5. 工程化落地：增量更新、双写一致性、兜底

### 增量更新

全量重建（删光重灌）逻辑简单，**几千 chunk、每周更新一次时真的是合理方案**，别不好意思用。天花板：百万 chunk 重算 embedding 十几小时、永远在重建路上、更新频率一高就死。规模/频率上来换增量（以文档为单位，谁变更新谁）。

**主键设计决定一切**，两种做法：

- **A：doc_id + chunk_index**（`refund-policy-v3:4`）——chunk 的位置即身份，更新=删旧 chunk 集+插新。**建议从 A 起步**：一个文档几十上百 chunk，全重算 embedding 就几秒，为省算力引入记账逻辑不划算。
- **B：内容 hash 参与主键**——没改的段落 hash 不变可跳过重算；代价是删除要靠新旧 hash 差集记账，复杂度实打实。算力真成账单大头再换。

**先删后插 vs upsert**：有个真坑——**upsert 只覆盖这次写了的主键，删不掉"上次有这次没有"的主键**。8000 字文档改成 3000 字，chunk 20→8，upsert 之后 9~20 号旧 chunk 还躺在库里，讲的还是旧内容。**残留比缺数据更阴：缺了顶多答不出，残留是理直气壮地答错**。整文档更新正确动作：按 doc_id 先 delete（ES delete_by_query / Milvus 表达式 delete）→ 切分新版权重算 → 批量插。这个顺序**天然幂等**——重试多少次结果都等于"该文档 chunk 集合=最新版"，是双写补偿的基石。upsert 留给 chunk 数不变的单条更新。先删后插有毫秒级空窗，按文档更新已从小时级缩到毫秒级，在意的再上"先插新延迟删旧"的复杂版。（原文：专栏四·05 第一节）

### 双写一致性：老问题，答案也一样

chunk 正文进 ES、向量进 Milvus，一次更新两次写入，一边成一边败。当年 MySQL+Redis 摔过的跟头。但先确认：**这里的不一致有多可怕？** 检索场景的后果是"用户多看一会儿旧版本/少召回一条"——烦人但不资损。**所以最终一致+异步补偿就够，别上分布式事务**（ES 近实时、Milvus 可调一致性，本来就不承诺写入立即可见，强一致无从谈起）。

老三样套上检索外衣：**文档库当 source of truth**（上游文档真身+元数据库）→ 同步程序监听变更，对 doc_id 执行先删后插、**同时作用 ES 和 Milvus** → 失败进重试队列（安全，因为幂等）→ **对账任务兜底**（重试也会一直失败，每天扫一遍 doc_id 版本对不对，对不上重新同步）。

### 降级兜底

混合检索的隐藏红利：**天然两份独立检索能力，一份挂另一份撑**——前提是把降级写出来（熔断器那套）：检测（超时+错误率阈值）→ 降级（Milvus 熔断走纯 BM25：语义检索受损但错误码型号不受影响；ES 熔断反向）→ 半开恢复。

两个决策：**降级要不要让用户知道**——内部工具建议悄悄降级+日志报警，面向客户的产品建议提示（产品判断不是技术判断）；**两边都挂怎么办**——答案没有商量余地：**报错，别硬答**。检索全失败=LLM 没有任何 grounding，裸答=开动幻觉制造机。宁明白提示"知识库不可用"，不让幻觉顶上。

### 监控

- **延迟分段看**：ES 路/Milvus 路/合并/rerank 各自 p50/p99——两路并发，端到端 ≈ 较慢那路 + rerank，哪个环节吃掉预算一眼可见。
- **空结果率单独打点**（最容易漏）：两路都返回 0 条时接口 200、无报错、SLO 全绿，但 LLM 拿着空上下文开始编。升高通常意味着：知识库没覆盖新话题/分词过滤出问题/某边存储悄悄没数据。**设告警阈值**。
- **质量基线**：离线评测集挂定时任务每周跑（数据在变，代码没动效果也会变）；线上 badcase 抽样回流。
- 存储层健康（ES heap/merge 压力、Milvus segment 加载/内存）按官方手册配常规告警。

## 最后，总结

RAG 实战五篇把整条链路收口：切分决定数据表示，是天花板（语义完整且单一，递归切分默认起点，元数据和正文一样重要）；BM25 的三处修正各自对应一个真实问题，它依赖全库统计量所以分数是相对量，两路合并因此只能用排名——RRF 用 1/(k+rank) 绕开所有分数量纲问题；rerank 是双塔与交叉编码的分工（召回要快要全靠预计算，精排要准靠交互），它救不了烂召回；评估让每次改动有数字背书，RAG 优先盯 recall@k，因为漏召回不可修复；工程化三件事——先删后插保幂等、最终一致加补偿别上分布式事务、降级单路兜底但全挂必须报错——每条都对应一类线上事故。

```text
━━━━━━━━━━ 一页纸背诵版 ━━━━━━━━━━
□ 切分决定数据表示，索引只在表示上做优化——切不对全白搭
□ chunk 矛盾：语义完整 + 语义单一
  · 太大=语义稀释(BM25被b惩罚)；太小=上下文碎
  · 递归切分=默认起点；overlap=给切不准买的保险
  · 元数据四件：doc_id(溯源+增量更新) title_path(免费语义锚点) chunk_index(邻居扩展) 权限标签
□ BM25 三修正：k1词频饱和(1.2) / b长度归一(0.75) / IDF平滑不翻负
  · 分数依赖全库统计量=相对量；余弦有界无绝对含义 → 两把尺子不能比
□ RRF：只用排名 1/(k+rank)，k=60 压低单路头部垄断，要"两路都说好"；偏心就加权
□ 单ES vs Milvus：百万内+已有ES→单ES；千万+/量化下盘/独立重负载→Milvus
□ 双塔=两段文本各自编码零交互(可预计算→召回)；cross-encoder=拼接过模型交互足(不可预计算→精排)
  · 漏斗：召回top10~20 → RRF合并20 → rerank出3~5
  · rerank 红利：量纲统一；分数不跨query比；救不了烂召回(先查在不在top20)
□ 指标：recall@k(该找到没) > hit rate(至少一条对的) > MRR(排多前)
  · RAG 优先 recall：漏召回不可修复(rerank见不到→LLM硬编)，排序粗糙可修复
  · 评测集：真实query最值(LLM生成要改口语化)；标准="单独能否直接回答"；badcase回流
□ RAGAS：忠实度(论断对检索内容核账) 答案相关性(反向生成问题) 上下文recall/precision
  · LLM裁判：离线抽样跑，换裁判=换尺子
□ 增量更新：A方案(doc_id+chunk_index)起步；整文档更新=先删后插(upsert删不掉变少的旧chunk→残留答错)
  · 先删后插天然幂等=双写补偿基石
□ 双写：检索比交易宽容(旧文档≠资损)→最终一致+重试+对账；文档库=source of truth
□ 降级：熔断一路单路撑；两边全挂必须报错，绝不让LLM裸答
□ 监控：延迟分段 / 空结果率单独打点(常规监控里永远"成功") / 评测集周跑基线
```
