# 00 实验环境：一次搭好，反复重置

先说清楚这个专栏对环境的三条约定，后面 17 个实验都建立在这三条上：

1. **一套固定环境**：所有实验共用一个单节点 ES（8.11.4）和一个 Milvus standalone（v2.4.4），版本钉死在镜像 tag 里。固定版本不是洁癖，是让文档里的"预期你会看到"有据可依——版本一漂，参数默认值、API 行为都可能悄悄变。
2. **每个实验自带材料构建**：不依赖任何其他实验留下的数据。任何一个实验，从"实验材料构建"小节照抄命令，就能从干净状态完整复现。
3. **搞砸就重置**：实验环境的第二条命是 `docker compose down -v`。`-v` 是关键——连数据卷一起删，回到出厂状态。实验失败的第一反应不该是修复脏数据，是重置重建。（当然，停下来想想为什么会砸，这一步才是实验的价值。）

## 一、环境清单

| 组件 | 版本（钉死） | 端口 | 用途 |
|------|-------------|------|------|
| Elasticsearch | 8.11.4，单节点，认证关闭 | 9200 | 实验 01~09、11、17 |
| Kibana | 8.11.4 | 5601 | Dev Tools 图形界面，实验 01 起 |
| Milvus standalone | v2.4.4 | 19530 / 9091 | 实验 03~15、17 |
| attu | v2.4 | 3000 | Milvus 图形界面，实验 03 起 |
| etcd / MinIO | v3.5.5 / RELEASE.2023-03-20T20-16-18Z | 不对外（MinIO 控制台 9001 除外） | Milvus 的元数据与对象存储 |
| 三节点 ES 集群 | 8.11.4 × 3，512m 堆 | 9210~9212 | 只给实验 10 用，独立 compose |
| Python | 3.10+ | - | 材料脚本与结果分析 |

说明一下 Milvus 身边那两个"内部"组件：Milvus 是存算分离架构，standalone 模式把 etcd（元数据）、MinIO（对象存储）和本体拉在同一个 compose 里，但它们是独立容器。这个结构本身就是[专栏三·06](../专栏三-运行机制/06-存算分离架构.md)的活教材——实验 03 你会打开 MinIO 控制台亲眼看它的数据，实验 16 还会再回去看索引文件。

## 二、compose 文件

真实文件在 [lab/docker-compose.yml](lab/docker-compose.yml)，内容如下（以文件为准）：

```yaml
services:
  es01:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.11.4
    container_name: es01
    environment:
      - discovery.type=single-node
      - xpack.security.enabled=false
      - ES_JAVA_OPTS=-Xms1g -Xmx1g
      - cluster.name=es-lab
    ports:
      - "9200:9200"
    volumes:
      - esdata:/usr/share/elasticsearch/data
    healthcheck:
      test: ["CMD-SHELL", "curl -sf http://localhost:9200/_cluster/health >/dev/null || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 12

  kibana:
    image: docker.elastic.co/kibana/kibana:8.11.4
    container_name: kibana
    environment:
      - ELASTICSEARCH_HOSTS=http://es01:9200
    ports:
      - "5601:5601"
    depends_on:
      es01:
        condition: service_healthy

  etcd:
    image: quay.io/coreos/etcd:v3.5.5
    container_name: milvus-etcd
    environment:
      - ETCD_AUTO_COMPACTION_MODE=revision
      - ETCD_AUTO_COMPACTION_RETENTION=1000
      - ETCD_QUOTA_BACKEND_BYTES=4294967296
      - ETCD_SNAPSHOT_COUNT=50000
    volumes:
      - etcd:/etcd
    command: etcd -advertise-client-urls=http://etcd:2379 -listen-client-urls http://0.0.0.0:2379 --data-dir /etcd

  minio:
    image: minio/minio:RELEASE.2023-03-20T20-16-18Z
    container_name: milvus-minio
    environment:
      MINIO_ACCESS_KEY: minioadmin
      MINIO_SECRET_KEY: minioadmin
    volumes:
      - miniodata:/minio_data
    command: minio server /minio_data --console-address ":9001"
    ports:
      - "9001:9001"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/minio/health/live"]
      interval: 30s
      timeout: 20s
      retries: 3

  milvus:
    image: milvusdb/milvus:v2.4.4
    container_name: milvus-standalone
    command: ["milvus", "run", "standalone"]
    environment:
      - ETCD_ENDPOINTS=etcd:2379
      - MINIO_ADDRESS=minio:9000
    volumes:
      - milvusdata:/var/lib/milvus
    ports:
      - "19530:19530"
      - "9091:9091"
    depends_on:
      - etcd
      - minio
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9091/healthz"]
      interval: 30s
      timeout: 20s
      retries: 5

  attu:
    image: zilliz/attu:v2.4
    container_name: attu
    environment:
      - MILVUS_URL=milvus:19530
    ports:
      - "3000:3000"
    depends_on:
      - milvus

volumes:
  esdata:
  etcd:
  miniodata:
  milvusdata:
```

三个值得看一眼的细节：

- `xpack.security.enabled=false`：实验环境关掉安全认证，curl 不用带账号密码。生产绝对不能这么干。
- `discovery.type=single-node`：单节点模式，跳过选主流程。实验 10 的三节点集群会把它换掉。
- MinIO 暴露了 9001 控制台端口：它本来就是 Milvus 的"内脏"，实验 03、16 要进去看数据。

## 四、重置协议

```bash
docker compose down -v
docker compose up -d
```

什么时候重置：实验做岔了、mapping 建错了改不回来（mapping 类型改不了，实验 06 会撞上这堵墙）、想验证"从零复现"。注意重置会清掉**所有实验**的数据——所以每个实验才都自带材料构建，重置不心疼。

## 五、Python 工具环境

```bash
cd lab
python -m venv .venv
source .venv/Scripts/activate
pip install -r requirements.txt
```

（Windows Git Bash 用 `source .venv/Scripts/activate`；PowerShell 用 `.venv\Scripts\Activate.ps1`；Linux/macOS 是 `source .venv/bin/activate`。）

依赖清单在 [lab/requirements.txt](lab/requirements.txt)：elasticsearch 客户端 8.12.1（对服务端 8.11 兼容）、pymilvus 2.4.4、numpy、matplotlib。

一个约定：文档里出现的每个 Python 脚本，真实文件都在 `lab/scripts/` 下（命名 `expNN-*.py`），照文件跑，别在 REPL 里一行行敲——实验要的是可复现。实验 17 需要额外装 sentence-transformers（会带 PyTorch CPU 版，约几百 MB），到那一篇时再装。

## 六、IK 中文分词插件（实验 05 前置）

ES 官方镜像不带中文分词，IK 插件装一下（只有实验 05 用到，其他实验可跳过）：

```bash
cd lab
bash install-ik.sh
```

脚本做两件事：下载与镜像版本对应的 analysis-ik 8.11.4 并安装、重启 es01。装完验证：

```bash
curl -s -X POST "http://localhost:9200/_analyze" -H "Content-Type: application/json" -d '{"analyzer": "ik_smart", "text": "苹果手机保护壳"}'
```

预期能看到切分出的多词 tokens（示意）。两个注意：插件版本号必须和镜像的 8.11.4 对齐，URL 里 404 就去 [IK 的 releases 页](https://github.com/medcl/elasticsearch-analysis-ik/releases)挑最接近的版本替换；插件装在容器层不在数据卷里，`down` 之后容器重建插件就没了，重跑一遍脚本即可。

## 七、三节点集群（实验 10 专用，进阶）

独立的 [lab/es-cluster.yml](lab/es-cluster.yml)：三个 ES 节点各 512m 堆，端口 9210~9212 和主环境错开，互不干扰（同时跑需要 8G+ 内存，不够就先把主环境 `docker compose down` 掉，实验 10 做完再回来）。

```bash
cd lab
docker compose -f es-cluster.yml up -d
curl "http://localhost:9210/_cat/nodes?v"
```

预期三行节点信息（示意）。这个集群不挂数据卷，每次 up 都是全新集群，做完 `docker compose -f es-cluster.yml down` 即可。

## 八、排错清单

- **ES 起不来，日志报 vm.max_map_count**：Linux 宿主机执行 `sudo sysctl -w vm.max_map_count=262144`；Docker Desktop（WSL2）默认已达标，一般撞不上。
- **端口占用**：9200/5601/3000/9001 被占说明本机已有同款服务在跑，停掉旧的或改 compose 的端口映射。
- **内存不够**：整套环境 5~6GB。Docker Desktop 分给 WSL2 的内存默认可能偏小，在 `%UserProfile%\.wslconfig` 里加 `memory=8GB` 后重启 Docker Desktop。
- **Milvus 反复重启**：先看 etcd 和 minio 健康没有（`docker compose ps`），Milvus 启动期最依赖这两个；仍不行用 `docker compose logs milvus` 看日志。
- **Kibana 一直"Server not ready yet"**：它要等 ES healthy 才起，通常一分钟内；超过三分钟看 `docker compose logs kibana`。
- **attu 打不开**：确认 milvus 容器 healthy；attu 连不上 Milvus 时页面会直接报错。

最后，总结：环境是实验的控制变量。版本钉死、状态可重置、每个实验自带材料——守住这三条，后面每个实验的"预期你会看到"才有意义。搭好了就进 [01-第一次见ES](01-第一次见ES-REST-API全景.md)。
