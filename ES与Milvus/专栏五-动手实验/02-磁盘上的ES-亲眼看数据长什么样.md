# 02 磁盘上的 ES：亲眼看数据长什么样

上一实验你写了 50 条文档、跑了一串 API，但它们对你来说还是黑盒：数据进了 9200 端口，在某个地方躺着，以 JSON 的形式回来。这一篇把盒子打开——进容器，亲眼看看 index、shard、segment 这三个词在磁盘上到底对应哪个目录、哪个文件。读完这一篇，这三个词从名词变成看得见的东西。

## 这个实验验证什么

index/shard/segment 不是三个抽象概念，是磁盘上三个嵌套的目录层级；`_cat/indices`、`_cat/shards`、`_cat/segments` 三个 API 视图和磁盘目录一一对应。顺便认识 Lucene 段文件家族（.si、.tim、.doc……各管什么）。

关联正文：[专栏三·02](../专栏三-运行机制/02-写入路径与近实时.md)（segment、merge、translog）、[专栏一·02](../专栏一-ES实战/02-核心概念与上手.md)（index/shard 概念）。上一实验：[01-REST API 全景](01-第一次见ES-REST-API全景.md)。

## 实验材料构建

前提：环境按 [00-实验环境](00-实验环境.md)起好，venv 激活，当前目录在 `lab`。

材料脚本 [lab/scripts/exp02-seed.py](lab/scripts/exp02-seed.py)：建 `exp02_index`，bulk 写 1000 条小文档，然后 force merge 成 1 个段——一次 bulk 写完会产生多个小段，目录里文件多而乱；合并成 1 个段后，段文件最干净，逐个数最方便：

```python
# exp02-seed.py —— 实验 02 材料：建 exp02_index，bulk 写 1000 条小文档，force merge 成 1 个段
# 用法：在 lab 目录的 venv 激活后运行 python scripts/exp02-seed.py
# 为什么 force merge：一次 bulk 写完会产生多个小段，合并成 1 个段后，
# 磁盘分片目录里的段文件最干净，逐个数文件最方便

import random

from elasticsearch import Elasticsearch
from elasticsearch.helpers import bulk

ES_URL = "http://localhost:9200"
INDEX = "exp02_index"
N = 1000


def main():
    es = Elasticsearch(ES_URL)
    if not es.ping():
        raise SystemExit("连不上 ES，先确认环境起来了：docker compose ps（在 lab 目录下执行）")

    es.indices.delete(index=INDEX, ignore=[400, 404])
    es.indices.create(
        index=INDEX,
        mappings={
            "properties": {
                "no":       {"type": "integer"},
                "title":    {"type": "text"},
                "category": {"type": "keyword"},
                "price":    {"type": "float"},
            }
        },
        settings={"number_of_shards": 1, "number_of_replicas": 0},
    )

    rng = random.Random(7)
    names = ["手机", "耳机", "电脑", "家电", "配件", "穿戴"]
    actions = [
        {
            "_index": INDEX,
            "_id": i,
            "_source": {
                "no": i,
                "title": f"商品编号{i:04d}",
                "category": names[i % len(names)],
                "price": round(rng.uniform(10, 2000), 2),
            },
        }
        for i in range(1, N + 1)
    ]
    success, errors = bulk(es, actions)
    es.indices.refresh(index=INDEX)

    # force merge：把所有段合并成 1 个（1000 条小文档，很快）
    es.indices.forcemerge(index=INDEX, max_num_segments=1)

    count = es.count(index=INDEX)["count"]
    print(f"exp02_index 就绪：写入 {success} 条，可搜索 {count} 条")
    print("下一步：GET /_cat/segments/exp02_index?v 验证只剩 1 个段，再去磁盘看文件")


if __name__ == "__main__":
    main()
```

跑它：

```bash
python scripts/exp02-seed.py
```

预期你会看到：

```text
exp02_index 就绪：写入 1000 条，可搜索 1000 条
下一步：GET /_cat/segments/exp02_index?v 验证只剩 1 个段，再去磁盘看文件
```

先验证合并生效（此时应该只剩 1 个段）：

```bash
curl -s "http://localhost:9200/_cat/segments/exp02_index?v"
```

预期你会看到（示意，节选）：

```text
index       shard prirep ip        segment generation docs.count docs.deleted   size size.memory committed searchable version compound
exp02_index 0     p      172.18.0.2 _2               2         1000            0 92.5kb      1.9kb true       true       9.8.0  false
```

## 实验步骤

### 第一步：从 API 拿到索引的 uuid

```bash
curl -s "http://localhost:9200/_cat/indices/exp02_index?v&h=index,uuid,pri,rep,docs.count,store.size"
```

预期你会看到（示意）：

```text
index       uuid                     pri rep docs.count store.size
exp02_index 3wLpXv6hQtSwMJ-ZO8DqzQ    1   0       1000     92.5kb
```

把 uuid 抄下来（你的值和示意不同），后面所有命令都用它。为省事可以赋给 shell 变量：

```bash
UUID=3wLpXv6hQtSwMJ-ZO8DqzQ
```

### 第二步：磁盘上找到 uuid 命名的目录

ES 的数据在容器里，路径 `/usr/share/elasticsearch/data`（compose 文件里挂到了 `esdata` 卷）。先看 indices 这一层：

```bash
docker compose exec es01 ls /usr/share/elasticsearch/data/nodes/0/indices
```

预期你会看到（示意）：

```text
2AaBbCcDdEeFfGgHhIiJjKk
3wLpXv6hQtSwMJ-ZO8DqzQ
FfEeDdCcBbAaZzYyXxWwVvU
```

目录名全是 uuid，没有一个是"exp02_index"。你刚才抄的 `3wLpXv6hQtSwMJ-ZO8DqzQ` 就在其中——**索引名是逻辑名，磁盘上只认 uuid**。另外两个目录是 demo_index（如果你跑过实验 01）和系统索引的，具体几个取决于你跑过哪些实验。

### 第三步：进分片目录

```bash
docker compose exec es01 ls /usr/share/elasticsearch/data/nodes/0/indices/$UUID
```

预期你会看到（示意）：

```text
0
_state
```

`0` 是**分片号**：exp02_index 只有 1 个主分片，所以只有 0 这一个目录。`_state` 稍后说，先往下钻一层：

```bash
docker compose exec es01 ls /usr/share/elasticsearch/data/nodes/0/indices/$UUID/0
```

预期你会看到（示意）：

```text
_state
index
translog
```

这一层就是分片的全部家当：`index/` 是索引数据（段文件住这）、`translog/` 是崩溃恢复的账本、`_state/` 是元数据。

### 第四步：认段文件

```bash
docker compose exec es01 ls /usr/share/elasticsearch/data/nodes/0/indices/$UUID/0/index
```

预期你会看到（示意，节选，以 8.11.4 实际行为为准）：

```text
_2.doc
_2.dvd
_2.dvm
_2.fdt
_2.fdx
_2.fnm
_2.liv
_2.pos
_2.si
_2.tim
_2.tip
segments_4
write.lock
```

两个先说在前面的变数：①段名前缀（这里的 `_2`）从几开始取决于内部计数，你看到 `_0`、`_3` 都正常，数字本身没有含义；②如果你的段很小，ES 可能把整段写成一个复合文件（一排 `_2.cfs`/`_2.cfe` 而不是这些散文件），那只是把一堆文件打包成一个，内容不变。

逐个文件过一遍（前缀 `_2.` 是段名，每个文件都从属于一个段）：

| 文件 | 是什么 | 你哪个操作在用 |
|------|--------|----------------|
| `segments_4` | 提交点：列出此刻有效的段。N 单调递增，每次 flush 换新文件 | flush（专栏三·02 的链路） |
| `_2.si` | 段元信息：这个段多少文档、由哪些文件组成、怎么来的 | 段被打开时读 |
| `_2.fnm` | 字段定义：mapping 落到物理层的样子，段里每个字段的编号、类型 | 写入时分词、查询时解析 |
| `_2.tim` | **term dictionary**：词典，所有词的有序列表 | 查词 |
| `_2.tip` | **term index**：词典的索引（FST），常驻内存，先查它定位 .tim 的块 | 查词的入口 |
| `_2.doc` | 词频 + 文档号：每个词出现在哪些文档、出现几次 | match 命中后读它 |
| `_2.pos` | 词位置：每个词在文档里的位置 | match_phrase 的顺序判断靠它 |
| `_2.fdt` | **_source 原文**：你写进去的 JSON 在这 | GET by id 还你原文 |
| `_2.fdx` | 原文的索引：按文档号定位 .fdt 里的块 | 同上，先查它 |
| `_2.dvd` | **doc values**：按列存的字段值（排序、聚合用） | sort price、聚合 |
| `_2.dvm` | doc values 的元信息 | 同上 |
| `_2.liv` | 活文档位图：每位一个文档，1 活 0 删。删除标记的家 | 查询结果过滤 |
| `write.lock` | 进程锁：防止两个 ES 进程打开同一个目录 | 单节点下你永远用不到，它防的是极端误操作 |

对着这张表再看一眼实验 01 的查询响应，链路就通了：`match title 蓝牙耳机` → FST（.tip）查到词 → .tim 拿 posting list → .doc 拿文档号 → .liv 过滤掉已删的 → .fdx/.fdt 挖出 _source 还给你。

### 第五步：API 视图对段文件

```bash
curl -s "http://localhost:9200/_cat/segments/exp02_index?v"
```

预期你会看到（示意）：

```text
index       shard prirep ip        segment generation docs.count docs.deleted   size size.memory committed searchable version compound
exp02_index 0     p      172.18.0.2 _2               2         1000            0 92.5kb      1.9kb true       true       9.8.0  false
```

`segment` 列的 `_2`，和第四步磁盘上那一排 `_2.*` 文件的前缀，一一对应。API 里的段名就是磁盘上的文件名前缀。

### 第六步：三视图对齐收口

三个 `_cat` API，三个视图，对应磁盘三层目录，串起来看：

| API 视图 | 命令 | 对应磁盘位置 | 看到的东西 |
|----------|------|--------------|-----------|
| 索引视图 | `_cat/indices`（uuid 列） | `data/nodes/0/indices/<uuid>/` | 逻辑索引 → uuid 目录 |
| 分片视图 | `_cat/shards`（shard 列） | `<uuid>/0/` | 分片 0 → 0 号目录 |
| 段视图 | `_cat/segments`（segment 列） | `<uuid>/0/index/_2.*` | 段 _2 → 一排段文件 |

拿实验 01 的 `_cat` 输出回来对照：`_cat/indices` 里 uuid 为 `3wLpXv6hQtSwMJ-ZO8DqzQ` 的行，磁盘上就有这个目录；`_cat/shards` 里 shard 0 那行，目录下就有 0 号分片目录；`_cat/segments` 里 `_2` 那行，index 目录里就躺着 `_2.si`、`_2.tim`……三个名词，三层目录，对齐完毕。

## 现象解释

**为什么索引名是逻辑名，磁盘只认 uuid。** 你 PUT 索引时 ES 分配一个 uuid，从此磁盘上的目录、集群元数据里都只认它。这么设计有个直接后果：索引的"名字"想换（比如灰度切流），不动目录、不搬数据——建个新索引，把 alias 从旧索引摘下来挂到新的，引用方零感知。ES 连"重命名索引"这个 API 都没有，alias 就是官方指定的改名方式；目录自诞生起就没打算变过。

**`_liv` 为什么值得单独盯一眼。** 这个索引你从没删过任何数据（docs.deleted 是 0），但它照样带着 `_2.liv`。机制上讲，删除在 Lucene 里从来不是"从段里抠掉"，是往位图里写 0；而 ES 内部对文档版本、恢复的簿记也会打这类标记，所以哪怕你一条没删，位图文件也在。位图什么时候真正派上用场——删一半数据看磁盘纹丝不动——实验 07 专门演给你看。

**`_state` 目录是什么。** 索引级元数据（mapping、settings 的落盘副本，属于 cluster state 的一部分），是"描述数据的数据"，不是文档数据本身。你可以把它理解为 MySQL 里 `frm`/数据字典那一层的东西，只是它和段文件住在同一个目录树下。

**`translog` 目录为什么和 index 平级。** 段文件在查询可见之前，先只进 page cache（近实时），磁盘上真正先落地的是 translog——每笔写操作先记这笔便宜的账，崩溃后靠它重放，30 分钟一次的 flush 才把持久性交给段文件。这就是[专栏三·02](../专栏三-运行机制/02-写入路径与近实时.md)那条 buffer → refresh → segment → flush 链路在磁盘上的住址。

**nodes/0 的 0 和 indices/<uuid>/0 的 0 不是一个 0。** 前者是节点序号（单节点所以只有 0；三节点会有 0、1、2），后者是分片号（1 主分片所以只有 0）。路径读法：节点 → 索引 → 分片 → 段文件，四级嵌套，一级一级把"数据到底在哪"收窄。

## 常见坑点

**1. 磁盘目录绝不能手改。** 段文件是一套互相引用的整体（segments_N 引着段，.si 引着文件清单），vim 一下、rm 一个，整个索引可能就起不来了。要看数据用 API，要删数据用 DELETE 请求，目录只读。

**2. Windows 宿主机看不到这个目录。** 数据在 `esdata` 卷里，落在 Docker 管的 WSL 虚拟磁盘内部，资源管理器里没有这条路。必须 `docker compose exec es01 ls ...` 进容器看，别浪费时间找挂载点。

**3. 段号对不上别慌。** `_0`、`_2`、`segments_4` 里的数字都是内部计数器，取决于你写过几轮、refresh 过几次，每次重置后都不同。对照的是**结构**（前缀一致），不是数字本身。

**4. docs.count 和文件对不上。** 刚写完的数据在 memory buffer 里，`_cat/indices` 的 docs.count 要 refresh 后才涨。近实时，不是文件系统出错。

**5. force merge 是实验操作，生产慎重。** 1000 条小文档秒级完成；但生产上对大索引 force merge 是重 IO 的动作，会挤占查询，而且把删除标记物理清掉的后果要想清楚（增量回收 vs 一次付清）。日常让后台 merge 自己干活，别伸手。

## 进一步实验

- **删一条试试（实验 07 前菜）**：`curl -s -X DELETE "http://localhost:9200/exp02_index/_doc/1"`，再看 `_cat/indices/exp02_index?v`——docs.count 少 1、docs.deleted 多 1、store.size 基本不动。删除是标记，磁盘不还你空间。
- **看 translog 长什么样**：`docker compose exec es01 ls /usr/share/elasticsearch/data/nodes/0/indices/$UUID/0/translog`——`translog-1.tlog` 之类，这就是那本崩溃恢复的账。
- **建一个 3 主分片的索引再来一遍**：settings 里 `number_of_shards: 3`，磁盘上分片目录会变成 0、1、2 三个，`_cat/shards` 多出两行——分片数建索引时定死这件事，眼见为实。

## 最后，总结

这一篇把实验 01 里那堆 JSON 落到了磁盘上：**索引是 uuid 目录，分片是数字目录，段是一排带统一前缀的文件**；`_cat/indices`、`_cat/shards`、`_cat/segments` 三个 API 视图和这三层目录一一对应。段文件各司其职——.tip/.tim 查词、.doc 拿命中、.fdx/.fdt 还原文、.dvd 排序聚合、.liv 记删除。顺手立了三条纪律：目录只读、变更走 API、force merge 是实验操作。下一篇去认识另一半地基：Milvus 的图形界面和 SDK——[03-第一次见Milvus](03-第一次见Milvus-attu与SDK全景.md)。
