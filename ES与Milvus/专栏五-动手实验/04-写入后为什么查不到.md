# 04 写入后为什么查不到

## 这个实验验证什么

一句话：**写入成功和搜索可见是两个时刻，中间隔着一个默认 1 秒的 refresh；而按 `_id` GET 不受这个间隔影响，它是实时的。**

机制依据在 [专栏三·02 写入路径与近实时](../专栏三-运行机制/02-写入路径与近实时.md)，"GET 实时、搜索近实时"这条差异在 [专栏一·02](../专栏一-ES实战/02-核心概念与上手.md) 里点过一次，这一篇我们把它亲手按在实验台上。

这个实验全程只需要 curl。第一步跑脚本建材料，后面的动作全部用 REST 请求做，写入和搜索之间隔了几秒、refresh 是自动来还是手动触发，全部由你亲手控制。

## 实验材料构建

```bash
cd lab
source .venv/Scripts/activate
python scripts/exp04-gen.py
```

脚本做三件事：建索引 `exp04_orders`（`order_no` 是 keyword，`content` 是 text）、bulk 灌 1000 条订单、手动 refresh 一次并打印 count。1000 条里有一部分正文含"退款"，这是后面搜索的目标词。预期输出：

```text
已创建索引 exp04_orders
bulk 写入 1000 条
refresh 后 count = 1000
材料构建完成
```

## 实验步骤

### 第 1 步：写入一条，立刻 GET

```bash
curl -s -X PUT "http://localhost:9200/exp04_orders/_doc/2001" -H "Content-Type: application/json" -d '{"order_no": "SO2026002001", "content": "客户申请退款，理由是七天无理由"}'
```

```json
{"_index":"exp04_orders","_id":"2001","result":"created","_shards":{"total":1,"successful":1,"failed":0}}
```

（示意，节选）

紧接着，不等任何时间，直接 GET：

```bash
curl -s "http://localhost:9200/exp04_orders/_doc/2001" | python -m json.tool
```

预期你会看到 `"found": true`，正文完整。注意这个请求离写入成功可能不到 100 毫秒——数据已经"在了"。

### 第 2 步：立刻搜索，搜不到

同样不等，马上搜：

```bash
curl -s -X POST "http://localhost:9200/exp04_orders/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"content": "退款"}}}' | python -m json.tool
```

预期你会看到（示意，节选）：

```json
{
  "hits": {
    "total": { "value": 253, "relation": "eq" },
    "hits": [ { "_id": "37" }, { "_id": "51" } ]
  }
}
```

total 不是 0——材料里约四分之一的正文含"退款"，它们在建材料阶段就被脚本 refresh 过了，搜得到很正常。但翻遍返回列表，`_id: 2001` 绝不在里面。GET 能找到它，search 找不到，数据是同一份。

### 第 3 步：等 2 秒，再搜

```bash
sleep 2
curl -s -X POST "http://localhost:9200/exp04_orders/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"content": "退款"}}}' | python -m json.tool
```

预期这次 2001 出现在 hits 里，`_score` 还排得不低。什么都没改，只是等了 2 秒。

### 第 4 步：手动 refresh，立即可见

再写一条 2002，然后不等，手动触发 refresh，再立刻搜：

```bash
curl -s -X PUT "http://localhost:9200/exp04_orders/_doc/2002" -H "Content-Type: application/json" -d '{"order_no": "SO2026002002", "content": "客户申请退款，重复扣款"}'
```

```bash
curl -s -X POST "http://localhost:9200/exp04_orders/_refresh"
```

```bash
curl -s -X POST "http://localhost:9200/exp04_orders/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"content": "退款"}}}' | python -m json.tool
```

预期 2002 已经在结果里，中间没有 sleep。是 refresh 把它变可见的，不是时间。

### 第 5 步：关掉自动 refresh

refresh_interval 是动态设置，不用重建索引，直接改：

```bash
curl -s -X PUT "http://localhost:9200/exp04_orders/_settings" -H "Content-Type: application/json" -d '{"index.refresh_interval": "-1"}'
```

```json
{"acknowledged": true}
```

再写 2003，等 5 秒（超过默认的 1 秒），再搜：

```bash
curl -s -X PUT "http://localhost:9200/exp04_orders/_doc/2003" -H "Content-Type: application/json" -d '{"order_no": "SO2026002003", "content": "客户申请退款，商品破损"}'
```

```bash
sleep 5
curl -s -X POST "http://localhost:9200/exp04_orders/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"content": "退款"}}}' | python -m json.tool
```

预期搜不到 2003。等多久都搜不到——`-1` 的意思不是"1 秒"，是"永不自动 refresh"。GET 一下试试，`"found": true`，数据完好。最后手动 refresh 一次把它捞出来：

```bash
curl -s -X POST "http://localhost:9200/exp04_orders/_refresh"
```

再搜，2003 可见。别忘了把设置改回来，否则这个索引后面会一直"丢数据"：

```bash
curl -s -X PUT "http://localhost:9200/exp04_orders/_settings" -H "Content-Type: application/json" -d '{"index.refresh_interval": "1s"}'
```

## 现象解释

把五个步骤串起来，就是[专栏三·02](../专栏三-运行机制/02-写入路径与近实时.md)那条链路：

1. 写入到达，文档进 memory buffer，操作追加进 translog，请求返回成功。这一刻文档**持久了**（translog 默认每请求 fsync），但**不可搜**。
2. 默认每 1 秒，一次 refresh 把 buffer 里的内容写成新的 segment，进文件系统缓存，对搜索打开。这一刻文档**可搜了**，但 segment 还没 fsync 到磁盘。
3. 所以第 2 步搜不到、第 3 步搜到了——中间隔的正是那次 refresh。第 4 步手动 `_refresh`，就是把"等 1 秒"这个动作换成"现在就做"。
4. 第 5 步的 `-1` 关掉的是自动 refresh，数据照样进 buffer、进 translog，只是永远不自动变成 segment。

那 GET 为什么一直找得到？GET 按 `_id` 取文档，这个操作不需要走倒排索引，ES 允许它在需要时直接读 translog 里的最新内容。所以"数据在不在"和"搜索能不能找到"走的是两条路：前者问 translog 和已打开的 segment，后者只问 refresh 之后的 segment。

一句话收口：**translog 保的是持久，refresh 保的是可搜，两件事被刻意拆开了。**你写完立刻 search 查不到，不是数据丢了，是链路还没走到那一步。

## 常见坑点

- **写完立刻 search 验证，查不到就以为代码有 bug。**这是新手的第一大误判来源。判断方法很便宜：先 GET 确认数据在，再手动 `_refresh` 后搜一次。两步之内就能把"数据没写进去"和"可见性时序"分开。养成习惯：任何"写入后马上查"的测试代码，要么加 `?refresh=wait_for`，要么接受最多 1 秒的延迟。
- **refresh_interval 改成 -1 之后忘了改回来。**批量导入的经典调优组合（-1 + 副本置 0）只该活在导入窗口内，导完必须恢复。忘改回来的症状很有迷惑性：写入全部成功，搜索"丢"一部分数据，监控还是绿的。
- **GET 得到就以为数据"可搜"了。**反过来也坑人：调试时用 GET 确认数据在，切到 search 又查不到，于是更困惑。记住这两个 API 语义不同，GET 实时、search 近实时。

## 进一步实验

refresh=wait_for 和手动 refresh，都是"读己之写"的手段，代价不同。写一条 2004，带上参数：

```bash
curl -s -X PUT "http://localhost:9200/exp04_orders/_doc/2004?refresh=wait_for" -H "Content-Type: application/json" -d '{"order_no": "SO2026002004", "content": "客户申请退款，待处理"}' | python -m json.tool
```

注意看返回耗时：这个 PUT 不会立刻返回，它会挂住，直到下一次 refresh 完成才回来——也就是说写入延迟被抬到了秒级。回来后立刻搜，不用任何等待，2004 已可见。和手动 refresh 的区别值得体会：手动 refresh 是"我现在逼它做一次"，wait_for 是"我等它自己做下一次"。对查询侧来说结果一样，对系统来说 wait_for 温和得多——10 个并发写都带 wait_for，也只是一起等同一次 refresh，而手动 refresh 可能逼出 10 个小 segment。具体调度行为以 8.11.4 实际为准。

## 最后，总结

- 写入成功 ≠ 立即可搜：中间隔着 refresh，默认 1 秒；GET 走 translog，实时。
- 手动 `_refresh` 立刻兑现可见性；`refresh_interval: -1` 关掉自动 refresh 后，数据永远"在"但永远搜不到，直到手动 refresh。
- 生产上"读己之写"要显式做：`?refresh=wait_for`（延迟换一致）或者接受 1 秒窗口，二选一，别靠碰运气。

下一篇我们换一个概念：分词。同一个字段、三种分词器，同一个词的 term 查询三种命运——那是中文搜索里命中率更高的一个坑。
