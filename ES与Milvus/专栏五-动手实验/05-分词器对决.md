# 05 分词器对决

> 前置：这个实验用到 IK 中文分词插件。没装的话先去 [00-实验环境](00-实验环境.md) 第六节跑一遍 `bash install-ik.sh`（装完验证那步成功了，这里就不会出意外）。

## 这个实验验证什么

一句话：**同一个词、同一个查询类型，换一个分词器就是另一种命运——term 查不到不一定是你查询写错，可能是字段的词表里根本没有这个词。**

概念依据是 [专栏一·03](../专栏一-ES实战/03-检索DSL查询写不对一切白搭.md) 的 term/match 分工和 [专栏一·04](../专栏一-ES实战/04-中文分词查不到的第一嫌疑人.md) 的中文分词。那两篇讲了机制，这一篇我们把三种分词器放上同一块场地，当面比一场。

## 实验材料构建

```bash
cd lab
source .venv/Scripts/activate
python scripts/exp05-gen.py
```

脚本建索引 `exp05_products`，`title` 是一个 multi-field，同一个值按三种分词器各存一份：

- `title.standard`：standard 分词器（ES 默认）
- `title.ik_max`：ik_max_word（最细粒度）
- `title.ik_smart`：ik_smart（最粗粒度）

然后灌约 20 条中文商品标题（苹果手机保护壳、苹果手机壳、中华人民共和国民法典精装版、一次性医用外科口罩50只装……其中 4 条含"苹果"）。预期输出：

```text
已创建索引 exp05_products（title: standard + title.ik_max + title.ik_smart）
bulk 写入 20 条
count = 20
材料构建完成
```

## 实验步骤

### 第 1 步：三种分词器切同一句话

先不下场查询，把三种分词器的刀法当面看一遍。用 `_analyze` 切同一句"苹果手机保护壳"：

```bash
curl -s -X POST "http://localhost:9200/_analyze" -H "Content-Type: application/json" -d '{"analyzer": "standard", "text": "苹果手机保护壳"}' | python -m json.tool
```

预期你会看到 tokens 是一串单字：苹 / 果 / 手 / 机 / 保 / 护 / 壳（示意，节选）：

```json
{
  "tokens": [
    { "token": "苹", "start_offset": 0, "end_offset": 1 },
    { "token": "果", "start_offset": 1, "end_offset": 2 }
  ]
}
```

standard 遵循 Unicode 的词边界标准，而中文的字与字之间没有边界信息，于是忠实地一字一切——这是[专栏一·04](../专栏一-ES实战/04-中文分词查不到的第一嫌疑人.md)讲过的机制。

换 ik_max_word：

```bash
curl -s -X POST "http://localhost:9200/_analyze" -H "Content-Type: application/json" -d '{"analyzer": "ik_max_word", "text": "苹果手机保护壳"}' | python -m json.tool
```

预期切出：苹果 / 手机 / 保护壳 / 保护 / 壳——嵌套的词全切出来，细粒度。再换 ik_smart：

```bash
curl -s -X POST "http://localhost:9200/_analyze" -H "Content-Type: application/json" -d '{"analyzer": "ik_smart", "text": "苹果手机保护壳"}' | python -m json.tool
```

预期切出：苹果 / 手机 / 保护壳——只挑最长的那条切分路径，粗粒度。

三份输出并排放着，对决已经开始了：同一个字段，切出三套词。切出来的词是什么？就是倒排索引词典里的词条。后面所有查询结果的差异，都从这三套词条上来。

### 第 2 步：term 查 standard 字段——0 条

```bash
curl -s -X POST "http://localhost:9200/exp05_products/_search" -H "Content-Type: application/json" -d '{"query": {"term": {"title.standard": "苹果"}}}' | python -m json.tool
```

预期你会看到：

```json
{
  "hits": {
    "total": { "value": 0, "relation": "eq" },
    "hits": []
  }
}
```

（示意，节选）

数据里明明有 4 个"苹果手机"开头的商品。term 拿"苹果"这个完整词条去 `title.standard` 的词典里找——词典里存的是苹、果两个单字，没有"苹果"。查不到，天经地义。

### 第 3 步：match 查同一个字段——查到了

字段都不换，只把 term 换成 match：

```bash
curl -s -X POST "http://localhost:9200/exp05_products/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"title.standard": "苹果"}}}' | python -m json.tool
```

预期 4 条命中，苹果手机保护壳、苹果手机壳这些都在。为什么这次行？match 在查询前先把"苹果"用这个字段同一个分词器（standard）切成了苹、果两个单字，拿单字去查单字词典——严丝合缝。记住这个命中数：第 4 步会给你一个结果一样、路径完全不同的对照组。

### 第 4 步：term 查 ik_max 字段——查到了

```bash
curl -s -X POST "http://localhost:9200/exp05_products/_search" -H "Content-Type: application/json" -d '{"query": {"term": {"title.ik_max": "苹果"}}}' | python -m json.tool
```

预期同样 4 条命中。这次 term 没有分词、原样拿"苹果"去查，却查到了——因为 ik_max_word 在**写入时**就把"苹果"作为一个完整词条切出来放进词典了。

term 查不到、term 查到了，差别不在查询写法，在字段写入时进了什么词。所以"term 要配 keyword 用"这条法则更完整的版本是：**term 配的是"词条"，而不是"类型"——keyword 整个值就是一个词条；分词的 text 字段，词条是切出来的词，term 能不能命中，取决于你要查的词有没有被完整切出来。**

### 第 5 步：match_phrase，顺序开始值钱

match 只问词在不在，match_phrase 还问位置挨不挨着。用 `title.ik_max` 试：

```bash
curl -s -X POST "http://localhost:9200/exp05_products/_search" -H "Content-Type: application/json" -d '{"query": {"match_phrase": {"title.ik_max": "手机壳"}}}' | python -m json.tool
```

预期能命中"苹果手机壳"：查询侧默认用同一个 ik_max_word 切，切成手机、壳两个词，而"苹果手机壳"这篇文档里手机、壳恰好相邻且顺序一致。

```bash
curl -s -X POST "http://localhost:9200/exp05_products/_search" -H "Content-Type: application/json" -d '{"query": {"match_phrase": {"title.ik_max": "壳手机"}}}' | python -m json.tool
```

预期 0 条。同样的两个字，顺序一反，词典里每个词都有、位置对不上，就是不命中。词的位置（position）平时看不见，但它一直在倒排索引里存着，match_phrase 就靠它吃饭。

（切分的具体词条和 position 数值以 8.11.4 实际输出为准——第 1 步的 `_analyze` 结果会告诉你确切切法。）

## 现象解释

把四场对决摆开看：

| 查询 | 字段 | 结果 | 为什么 |
|------|------|------|--------|
| term 苹果 | standard | 0 | 词典里只有单字 |
| match 苹果 | standard | 4 | 查询也被切成单字，对上了 |
| term 苹果 | ik_max | 4 | 词典里真有"苹果"这个词条 |
| match_phrase 壳手机 | ik_max | 0 | 词都在，位置不对 |

规律就一条：**查询用的词条，必须和词典里的词条一模一样，才能碰头。**term 和 match 的分工（term 不分词、match 用字段的 search_analyzer 分词）决定了谁负责对齐词条；分词器的粒度决定了词典里有什么词条。

生产上最经典的组合从这场对决直接推出来：**索引用 ik_max_word，搜索用 ik_smart。**索引侧把所有粒度的词都存进词典，用户不管搜"保护壳"还是"壳"都能召回；搜索侧用粗粒度切查询，词条少、干扰少。反过来配就是事故配置——词典里只有粗词，查询切成细词，全 miss。

## 常见坑点

- **text 字段用 term 查整词，十有八九查不到。**第 2 步已经演过了。term 的正确对象是 keyword 字段、数字、日期，或者第 4 步那种"你明确知道词条长什么样"的场景。默认动态映射对字符串是 text + keyword 子字段双存，精确匹配查 `字段.keyword`。
- **索引分词和搜索分词不一致，静悄悄返回 0 条。**mapping 里配了 `analyzer: ik_max_word, search_analyzer: ik_smart`，某天有人在查询里显式写了 `"analyzer": "standard"`，从此查不到，不报错、不告警。防御姿势：分词配置只在 mapping 一处定义，查询代码里永远不写 analyzer 参数。排查用 `_analyze` 三连（[专栏一·04](../专栏一-ES实战/04-中文分词查不到的第一嫌疑人.md)第四节的三步流程）。
- **改分词器不生效于旧数据。**mapping 的 analyzer 和字段类型一样不可变，已写入的文档在 segment 里已经按老分词器切好了。换 IK 只能建新索引 + reindex 搬数据，只改 mapping（如果改得动的话）只对之后写入的文档生效。这个坑和实验 06 的类型坑是同一个根源。

## 进一步实验

把搜索侧分词器换掉，看命中变化。`search_analyzer` 是少数可以事后改的 mapping 参数（只影响查询端，不用动数据）：

```bash
curl -s -X PUT "http://localhost:9200/exp05_products/_mapping" -H "Content-Type: application/json" -d '{"properties": {"title": {"type": "text", "analyzer": "standard", "fields": {"ik_max": {"type": "text", "analyzer": "ik_max_word", "search_analyzer": "standard"}}}}}'
```

然后 match 查 `title.ik_max` 搜"苹果手机"：索引侧的词条还是 ik 切出的词（苹果、手机……），查询侧被 standard 切成苹/果/手/机四个单字，拿单字去查 ik 的词典——预期 0 命中。一次改动，亲眼看到"两端不一致"是怎么把搜索打成 0 的。改完记得再改回 `ik_max_word`（同一个 PUT 把 search_analyzer 换回去即可；search_analyzer 可动态修改这一点以 8.11.4 实际行为为准）。

## 最后，总结

- 三种分词器三种刀法：standard 中文逐字切，ik_max_word 全粒度都切，ik_smart 挑最粗路径。
- term/match 的本质分工：match 才会用字段配置的 analyzer 切查询串去对齐词条；term 拿原值硬查。查不到的第一嫌疑永远是"词条没对上"。
- 经典组合：索引 ik_max_word（召回多粒度）+ 搜索 ik_smart（查询精准）；两端不一致 = 静悄悄的 0 命中。
- 换分词器 = reindex，旧数据永远停在旧切法里。

下一篇还是坑，而且更隐蔽：不写 mapping 直接灌数，ES 会"贴心地"替你把类型猜好——猜对了皆大欢喜，猜错了你连报错都等不到。
