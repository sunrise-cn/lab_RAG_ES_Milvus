# 06 动态映射的坑

## 这个实验验证什么

一句话：**动态映射下，索引里第一条数据替你把 schema 定终身——类型猜错了不能原地改，唯一的路是 reindex；更阴的是有些错连报错都不给你。**

概念依据是 [专栏一·02](../专栏一-ES实战/02-核心概念与上手.md) 第四节"动态映射：最舒服的坑"。那一篇讲了翻车现场，这一篇我们把每种翻车方式亲手复现一遍，最后走一遍完整的修复路径。全程 curl，不需要脚本。

## 实验材料构建

材料就是几个干净的空索引，边做边建。唯一要确认的是旧实验残留别撞车，先清一遍：

```bash
curl -s -X DELETE "http://localhost:9200/lab_dynamic,lab_dynamic2,lab_dynamic3,lab_dynamic_strict,lab_dynamic_false,lab_orders_v2?ignore_unavailable=true"
```

```json
{"acknowledged": true}
```

（`ignore_unavailable=true` 让不存在的索引不报 404，重跑也不炸。）

## 实验步骤

### 第 1 步：一条数据，schema 定终身

不写 mapping，直接灌第一条数据：

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic/_doc/1" -H "Content-Type: application/json" -d '{"order_no": "A001", "price": 12.5, "created": "2026-01-01"}'
```

然后看 ES 替你"猜"出了什么：

```bash
curl -s "http://localhost:9200/lab_dynamic/_mapping" | python -m json.tool
```

预期你会看到（示意，节选）：

```json
{
  "lab_dynamic": {
    "mappings": {
      "properties": {
        "order_no": {
          "type": "text",
          "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } }
        },
        "price": { "type": "float" },
        "created": { "type": "date" }
      }
    }
  }
}
```

三个字段三个故事：`order_no` 是字符串，动态映射给字符串的默认待遇是 text + keyword 子字段双存；`price` 是 JSON 浮点数，映射成 float；`created` 最值得盯一眼——**它只是长得像日期的字符串，ES 的 date detection 默认开着，"2026-01-01" 被 dynamic mapping 识别成了 date**。你一行类型都没写，三个字段的物理存储结构已经定了。

### 第 2 步：类型定了，脏数据就进不来了

再写一条 `created` 不是日期的：

```bash
curl -s -X PUT "http://localhost:9200/lab_dynamic/_doc/2" -H "Content-Type: application/json" -d '{"order_no": "A002", "price": 88.0, "created": "不是日期"}'
```

预期 400，返回里带着 `mapper_parsing_exception`，说 failed to parse field [created]（示意，节选）：

```json
{
  "error": {
    "type": "mapper_parsing_exception",
    "caused_by": {
      "type": "illegal_argument_exception",
      "reason": "failed to parse date field [不是日期]"
    }
  },
  "status": 400
}
```

报错拦住了脏数据，这算好的一面。代价是：这个字段从此只能放日期。你要是本来就想把它当普通字符串存，第一条数据已经把路堵死了——而这只是麻烦的开始，真正阴的坑在下一步。

### 第 3 步：不报错的坑——字符串数字

新建索引 `lab_dynamic2`，第一条数据把 amount 写成字符串 `"12.5"`——引号加了、内容是数字，这是上游数据最常见的脏法：

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic2/_doc/1" -H "Content-Type: application/json" -d '{"amount": "12.5"}'
```

看一下 mapping：

```bash
curl -s "http://localhost:9200/lab_dynamic2/_mapping" | python -m json.tool
```

预期 `amount` 是 text（带 keyword 子字段）——字符串嘛。现在写一个真数字进去：

```bash
curl -s -X PUT "http://localhost:9200/lab_dynamic2/_doc/2" -H "Content-Type: application/json" -d '{"amount": 15.5}' | python -m json.tool
```

预期你会看到 `"result": "created"`——**写入成功了，没有任何报错**。GET 出来看，`_source` 里 amount 还是数字 15.5（`_source` 存的是你发来的原文）。但索引里已经是另一回事了，拿 term 查字符串验证：

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic2/_search" -H "Content-Type: application/json" -d '{"query": {"term": {"amount": "15.5"}}}' | python -m json.tool
```

预期能查到 `_id: 2`。_source 里是数字，词典里却是字符串 "15.5"——ES 把 15.5 静默强转成字符串收下了（coerce 默认开）。"没报错"不代表类型是对的，数据在索引侧已经变形了。等到有一天你想对 amount 排序、聚合，才会在 text 字段上撞墙——那时已经几十万条数据住进来了。

### 第 4 步：报错的坑——数字字段进字符串

反过来再试一次。新索引 `lab_dynamic3`，第一条先写真数字：

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic3/_doc/1" -H "Content-Type: application/json" -d '{"amount": 12.5}'
```

这次 `amount` 是 float。再写一条带单位的字符串：

```bash
curl -s -X PUT "http://localhost:9200/lab_dynamic3/_doc/2" -H "Content-Type: application/json" -d '{"amount": "12.5元"}' | python -m json.tool
```

预期 400，`mapper_parsing_exception`，float 解析失败。和第 2 步一个道理：类型已定，来路不对的值要么被强转，要么被拒绝——赌哪种全看第一条数据。

### 第 5 步：dynamic 三种模式

先猜一个问题：新字段来了，ES 除了"猜"，还有别的态度吗？有，`dynamic` 参数就是态度开关。对照着做三个索引。

**strict：不认识就拒收。**

```bash
curl -s -X PUT "http://localhost:9200/lab_dynamic_strict" -H "Content-Type: application/json" -d '{"mappings": {"dynamic": "strict", "properties": {"order_no": {"type": "keyword"}}}}'
```

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic_strict/_doc/1" -H "Content-Type: application/json" -d '{"order_no": "A001", "surprise": "hello"}' | python -m json.tool
```

预期 400，报 strict_dynamic_mapping_exception，错误信息里会把拒绝的字段名列出来，就像一次"写入前的 dry run"。

**false：不认识就丢弃（静默）。**

```bash
curl -s -X PUT "http://localhost:9200/lab_dynamic_false" -H "Content-Type: application/json" -d '{"mappings": {"dynamic": "false", "properties": {"order_no": {"type": "keyword"}}}}'
```

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic_false/_doc/1" -H "Content-Type: application/json" -d '{"order_no": "A001", "surprise": "hello"}' | python -m json.tool
```

预期返回 `"result": "created"`，写入成功。但搜 surprise 试试：

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic_false/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"surprise": "hello"}}}' | python -m json.tool
```

预期 0 命中，不报错。字段没进倒排索引——`_source` 里有、词典里没有，存了但搜不了。注意 false 和 strict 是两种不同的哲学：false 是"多余的我不管但别报错"，strict 是"多余的就是事故，当场报出来"。

**true（默认）：不认识就现猜。**第 1 步已经演过了，就是它。

### 第 6 步：修复路径——显式 mapping + reindex

现在把 lab_dynamic 的正确打开方式走一遍。第 1 步里 `created` 被 date detection 误判（假设业务上它该是普通字符串），改是改不动的——为什么改不动下一节说。路只有一条：建新索引、写对 mapping、把数据搬过去。

```bash
curl -s -X PUT "http://localhost:9200/lab_orders_v2" -H "Content-Type: application/json" -d '{"mappings": {"properties": {"order_no": {"type": "keyword"}, "price": {"type": "double"}, "created": {"type": "keyword"}}}}'
```

注意两点：`order_no` 显式声明成 keyword（精确匹配场景用不着分词）；`created` 明确声明成 keyword——date detection 只在动态映射时生效，显式声明让"猜"彻底出局。然后搬家：

```bash
curl -s -X POST "http://localhost:9200/_reindex" -H "Content-Type: application/json" -d '{"source": {"index": "lab_dynamic"}, "dest": {"index": "lab_orders_v2"}}' | python -m json.tool
```

预期你会看到（示意，节选）：

```json
{
  "took": 123,
  "total": 1,
  "updated": 0,
  "created": 1,
  "failures": []
}
```

`failures` 空数组就是搬迁全部成功。验证一下新 mapping 和数据：

```bash
curl -s "http://localhost:9200/lab_orders_v2/_mapping" | python -m json.tool
```

```bash
curl -s "http://localhost:9200/lab_orders_v2/_count"
```

预期 count 是 1（lab_dynamic 里第 2 步那条脏数据被 400 拦下了，从没写进去过），`created` 已经是 keyword，第 2 步那个"不是日期"现在写得进去了——因为类型本身变了。生产上完整流程还有最后两步：别名切换、删旧索引，这里数据只有一条就不展开了，路子是一样的。

## 现象解释

先看识别规则。动态映射按 JSON 类型套 ES 类型：浮点数给 float，整数给 long，true/false 给 boolean。字符串麻烦一点，要过两道关：先过 date detection（默认开），长得像日期就给 date；不像的走最后一条路，text + keyword 双存。第 1 步三个字段就是这么定出来的。

再回答那个大问题：为什么类型不能原地改？回想实验 02 在磁盘上亲眼看到的那些文件——segment 里的 `.tim` 是词典、`.doc` 是文档表。`price` 定成 float 那一刻起，12.5 就按 float 的数值编码写进了 segment 的 BKD 树；`order_no` 定成 text，就已经被分词、进了词典和 posting list。改类型等于换一套物理结构，而 segment 不可变（[专栏三·02](../专栏三-运行机制/02-写入路径与近实时.md)）——旧数据按老结构躺在磁盘上，原地改只是把新写入换编码，新旧两套编码在一个字段里混着，查询直接乱套。所以 ES 干脆不许改，要换结构就整体重写，重写就是 reindex。

最后是 dynamic 三种模式怎么选。日志、探索性数据、字段乱七八糟的第三方数据，true 省心；长期服务的业务索引，strict 把 schema 的决定权从"第一条数据"手里拿回来；false 居中——接受新字段存在但不为它建索引，写入不炸、索引不膨胀，代价是搜不到。

## 常见坑点

- **生产直接灌数让 ES 自动建 mapping。**等于把 schema 决定权交给第一条碰巧到达的数据。第 3 步已经看到，第一条错了，后面连报错都是"看情况"的。业务索引铁律：先手写 mapping 再灌数。
- **date detection 误伤。**"2026-01-01" 被识别成 date 是贴心，但类似的边缘格式被识别就是误伤。版本号 "1.2.3" 不会被识别成 date（不是合法日期格式），但要小心 "2026.01" 这类长得像日期的取值——凡是"字符串但内容像日期"的字段（单号、编号、备注里的日期字符串），显式声明 keyword 才稳。具体识别规则清单以官方文档 dynamic mapping 一节为准。
- **coerce 的静默强转。**第 3 步那 15.5 变 "15.5" 是最阴的坑：不报错、有数据、能查询，等你发现时错误类型已经陪着数据住进来了。防线只有一道：显式 mapping + 上线前 `GET _mapping` 亲自过一遍。
- **改类型只能 reindex，且 reindex 期间双写或停写要想清楚。**reindex 是一次快照搬迁，源索引继续写入的部分不会自己跟过去，生产切换要么双写、要么别名 + 短暂停写。没有银弹，只有权衡。

## 进一步实验

numeric_detection 打开后看字符串数字的下场。新建索引，settings 里把 `numeric_detection` 打开（它是 index 级动态映射设置，建索引时放进 settings）：

```bash
curl -s -X PUT "http://localhost:9200/lab_dynamic_num" -H "Content-Type: application/json" -d '{"mappings": {"numeric_detection": true}}'
```

```bash
curl -s -X POST "http://localhost:9200/lab_dynamic_num/_doc/1" -H "Content-Type: application/json" -d '{"amount": "12.5"}'
```

```bash
curl -s "http://localhost:9200/lab_dynamic_num/_mapping" | python -m json.tool
```

预期 `amount` 这次是 float 而不是 text——numeric_detection 让"长得像数字的字符串"也参与类型推断。方向和 date detection 一致：识别越激进越省心，也越容易误伤。到底开不开，看你敢不敢把字段类型交给数据的长相。

## 最后，总结

- 首条数据定类型终身：date detection 默认开，"2026-01-01" 这样的字符串直接变 date；类型一进 segment 就是物理结构，改不了，只能 reindex。
- 报错的坑好过不报错的坑：float 进"12.5元"当场 400，text 吞 15.5 静默强转——后者发现时已经晚了。
- dynamic 三模式：true 赌运气，false 存而不索引，strict 把 schema 决定权拿回自己手里。业务索引：显式 mapping + strict，上线前 `GET _mapping` 亲自过。
- 修复路径固定四步：新索引 + 显式 mapping → reindex → 验证 → 别名切换。
