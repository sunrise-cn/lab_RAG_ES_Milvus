# 08 BM25 打分手感

## 这个实验验证什么

一句话：**BM25 的分数不是词频的线性函数——出现 5 次只比出现 1 次高不到 2 倍（k1 饱和）；同样出现一次，短文档压长文档（b 长度归一）。**

机制依据是 [专栏一·05 相关性打分](../专栏一-ES实战/05-相关性打分让好结果排前面.md)里"BM25 的直觉版"和 [专栏四·02](../专栏四-RAG实战/02-BM25算法与混合检索.md)的公式拆解：k1 控制词频饱和，b 控制长度惩罚。正文说"第 10 次出现几乎不涨分"，这一篇我们用 `_explain` 把每一分钱拆开数。

全程只用 curl，不需要脚本。

## 实验材料构建

### 设计：内容故意造得像填字游戏

控制变量优先于可读性，所以材料很假，假得有意为之。8 条文档，分三组：

| `_id` | elasticsearch 出现次数 | 总长度（token 数） | 用途 |
|-------|----------------------|------------------|------|
| a1 | 1 | 41 | 词频组 |
| a3 | 3 | 41 | 词频组 |
| a5 | 5 | 41 | 词频组 |
| a10 | 10 | 41 | 词频组 |
| b_short | 1 | 9 | 长度组（短） |
| b_long | 1 | 81 | 长度组（长） |
| c1 | 0 | 41 | 对照组 |
| c2 | 0 | 41 | 对照组 |

三处设计意图：

1. **词频组四条等长**（都是 41 token），唯一变量是关键词出现次数——词频的影响被单独拎出来。
2. **长度组两条等词频**（都是 1 次），唯一变量是长度。
3. **关键词用英文词 `elasticsearch`**：standard 分词器把它切成一个完整 token，一次出现就是一次词频。如果用中文"退款"，standard 会拆成"退"和"款"两个 term，match 查询的分数是两个 term 的 BM25 之和，解释起来多绕一层。另外加两条不含关键词的对照文档（c1、c2），让"elasticsearch"这个 term 的文档频率（6/8）不那么极端，idf 不至于贴着 0。

填充词用 `filler`——standard 分词器下一个英文单词一个 token，数起来精确。每条文档 = 关键词若干次 + 填充词若干次，总长恒定。

## 实验步骤

### 第 1 步：搜一次，看分数的"不成比例"

```bash
curl -s -X POST "http://localhost:9200/exp08-bm25/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"content": "elasticsearch"}}}' | python -m json.tool
```

预期你会看到（示意，节选；分数按 BM25 公式手算，你的环境会有小数位差异）：

```json
{
  "hits": {
    "total": {"value": 6, "relation": "eq"},
    "hits": [
      {"_id": "a10", "_score": 0.291},
      {"_id": "a5",  "_score": 0.263},
      {"_id": "a3",  "_score": 0.234},
      {"_id": "b_short", "_score": 0.218},
      {"_id": "a1",  "_score": 0.149},
      {"_id": "b_long",  "_score": 0.107}
    ]
  }
}
```

对着这六个数看三件事：

1. **a10 的词频是 a1 的 10 倍，分数只有 1.95 倍。**a5 是 a1 的 5 倍词频，分数只有 1.77 倍。如果你带着 TF-IDF 的线性直觉来，预期落空了——这不是 bug，是 BM25 的设计。
2. **a 组四条等长**，排序完全跟词频一致：1 < 3 < 5 < 10。词频还是有用的，只是边际递减。
3. **b_short 和 b_long 同样只出现一次**，短文分数是长文的两倍。而且 b_short（只有 9 个 token、词频 1）压过了 a1（41 个 token、词频 1）——长度归一在起作用。

把 a5 的 `_explain` 也跑一遍，两个摆在一起看 tf 项（示意）：

| `_id` | freq | tf 项 | 最终分 |
|-------|------|-------|--------|
| a1 | 1 | 0.459 | 0.149 |
| a3 | 3 | 0.718 | 0.234 |
| a5 | 5 | 0.809 | 0.263 |
| a10 | 10 | 0.894 | 0.291 |

idf 一列四条完全相同（0.325——同一 term、同一批文档，idf 只跟词的全库分布有关）。dl 也相同（41）。**唯一变化的是 freq，而 tf 项从 0.459 爬到 0.894 就封顶在望**：代入公式，freq 趋向无穷时 tf 项趋向 1——这条曲线有天花板，词频堆得再多也就买满 1。

### 第 3 步：_explain 拆 b_short 和 b_long，对比长度项

```bash
curl -s -X POST "http://localhost:9200/exp08-bm25/_explain/b_short" -H "Content-Type: application/json" -d '{"query": {"match": {"content": "elasticsearch"}}}' | python -m json.tool
```

再对 b_long 跑一遍。两条的 freq 都是 1、idf 相同，唯一不同的是 tf 项里那段长度归一（示意）：

| `_id` | freq | dl | avgdl | tf 项 | 最终分 |
|-------|------|-----|-------|-------|--------|
| b_short | 1 | 9 | 42 | 0.670 | 0.218 |
| b_long | 1 | 81 | 42 | 0.329 | 0.107 |

同样的词频，dl 从 9 涨到 81，tf 项直接砍半。分数差距全部来自 `dl / avgdl` 那一项。

## 现象解释

Lucene 的 BM25 实现里，一个 term 的得分是三部分相乘（`boost * idf * tf`，boost 默认 1）：

**idf 项**：`log(1 + (N - n + 0.5) / (n + 0.5))`。只跟这个词的"全库分布"有关——8 条文档里 6 条都有 elasticsearch，它不算稀有词，idf 只有 0.325。如果只有 1 条文档有它，这个值会是 2 左右（量级示意）。这就是"稀有词值钱"的数学化身，两个实验组里它纹丝不动，恰好证明它跟词频、长度无关。

**tf 项**：`freq / (freq + k1 * (1 - b + b * dl / avgdl))`。分两半看：

- **k1 那一半（分子分母里的 k1）管饱和**。k1=1.2 时，freq=1 的 tf 项是 0.46，freq=5 是 0.81，freq=10 是 0.89，freq=100 也才 0.988——多出来的每一次出现，买到的增量越来越少。这就是[专栏四·02](../专栏四-RAG实战/02-BM25算法与混合检索.md)说的"第一次出现最有信息量，第十次几乎白给"。堆词频提排名在 BM25 下天然低效，这是反 SEO 的设计，不是缺陷。
- **b 那一半（dl/avgdl 那段）管长度**。b=0.75 时，长度影响打七五折。同样一次命中，出现在 9 token 的短文里 tf 项 0.67，出现在 81 token 的长文里 0.33——长文档被按比例摊薄了"含金量"。翻译成 RAG 的语言：chunk 切太大，同样的关键词命中被长度归一惩罚，排名吃亏——chunking 篇讲的"切太大被罚"，罚的就是这里。

最后把第 1 步那六个数重新读一遍：BM25 不是"关键词出现多就赢"，而是"在多长的一篇文档里、以多高的密度命中了一个多稀有的词"。三个因子互相牵制，你在 `_explain` 里看到的就是这个乘法的逐项展开。

## 常见坑点

- **拿 TF-IDF 的线性直觉写业务**。典型症状："客户想让某篇文档排前面，就多塞几遍关键词"——塞 10 遍只比塞 1 遍多 95% 的分（本实验 a10 vs a1），塞 50 遍和塞 10 遍几乎没差别。想置顶该用 boost 或 function_score（[专栏一·05](../专栏一-ES实战/05-相关性打分让好结果排前面.md)第三、四节），别在词频上死磕。
- **以为 match 查询的分数和词频成正比**。多词查询的分数是每个 term 的 BM25 之和，而每个 term 内部又各自饱和。分数是"乘法结构 + 饱和曲线"，任何"翻倍词频该翻倍分数"的断言都不成立，拿实验数据说话。
- **忽略长度归一就去调 chunk 大小**。做 RAG 时 chunk 从 200 字调到 800 字，同样的关键词命中分数明显下滑，以为是"内容稀释了"，其实一半是 b 项在按 avgdl 摊薄。avgdl 是全库平均——**新增一批长文档会改变旧文档的得分**，因为 avgdl 变了。这个"改数据不改查询，分数也会漂"的现象排错时非常迷惑人。
- **跨查询比分数大小**。`_score` 只在同一次查询内有意义，换个查询词、库的统计量一变，绝对值就对不上。实验里那些 0.149、0.291 也一样——它们的意义是本次查询内的相对次序，不是"文档质量 29%"。

## 进一步实验

把两个参数分别"关掉"，看分数怎么变。similarity 是 mapping 级设置，改不了在位的，建两个变体索引：

```bash
curl -s -X PUT "http://localhost:9200/exp08-k1zero" -H "Content-Type: application/json" -d '{
  "settings": {"number_of_shards": 1, "number_of_replicas": 0},
  "mappings": {"properties": {"content": {"type": "text", "similarity": {"type": "BM25", "k1": 0, "b": 0.75}}}}
}'
```

k1=0 代进 tf 公式，分母的 k1 项消失，tf 项恒等于 1——**词频完全失效**。把 a 组四条文档原样灌进去（bulk 那段照抄，`_index` 换成 exp08-k1zero），搜索后预期四条 `_score` 一模一样。这从反面证明 a 组的分数差全部由 k1 项贡献。

照同样方法建 `exp08-b0`（`"b": 0`，k1 保持 1.2），灌 b_short 和 b_long，预期两条分数一样——b=0 时公式里不再有 dl/avgdl，长度归一关闭。（k1/b 允许的取值范围和版本行为以官方文档为准。）

## 最后，总结

- 词频饱和：freq 从 1 到 10，tf 项从 0.46 爬到 0.89，天花板是 1——堆词频买不到线性回报。
- 长度归一：同样一次命中，9 token 短文的 tf 项（0.67）是 81 token 长文（0.33）的两倍——chunk 切太大被罚，罚在这。
- `_explain` 把 `boost * idf * tf` 摊开：idf 看全库分布，tf 看词频和长度，两个参数 k1=1.2、b=0.75 白纸黑字写在返回里。
- 分数是相对量：同一查询内比次序可以，跨查询、跨库比大小不行。
