# 09 深分页的墙

## 这个实验验证什么

一句话：**`from + size` 翻到 10000 条就撞墙（`index.max_result_window` 默认 10000）；就算不撞墙，翻得越深越慢、分片越多越慢——每个分片都要白取 `from + size` 条再被协调节点归并扔掉；正确的深遍历姿势是 PIT + search_after。**

机制依据是 [专栏三·03 查询执行流程](../专栏三-运行机制/03-查询执行流程.md)的"query then fetch 两阶段"和"深度分页的代价"两节。正文里那笔账（"翻第 N 页的代价是每页都按全量名次算"）是推理，这一篇我们拿 30 万条数据当面验。

## 实验材料构建

```bash
cd lab
source .venv/Scripts/activate
python scripts/exp09-gen.py
```

脚本（[exp09-gen.py](lab/scripts/exp09-gen.py)）建两个索引、各灌 30 万条（`no` 是 long，`text` 是 text），除了分片数其他完全一致：

- `exp09_one`：1 个主分片
- `exp09_five`：5 个主分片

`_id` 显式用 `no`，路由公式 `hash(_id) % 主分片数` 会把 30 万条近似均匀摊到各分片——两个索引装的是同一批内容，唯一变量是分片数。预计 1~2 分钟，预期输出（示意，节选）：

```text
已创建索引 exp09_one（1 分片），开始写入 300000 条
bulk 写入 300000 条，refresh 后 count = 300000，耗时 28s
已创建索引 exp09_five（5 分片），开始写入 300000 条
bulk 写入 300000 条，refresh 后 count = 300000，耗时 31s
材料构建完成
```

副本都设为 0——单节点环境副本无处安放（实验 10 会专门看这件事），别让 yellow 状态干扰本实验。

## 实验步骤

### 第 1 步：直接撞墙

```bash
curl -s -X POST "http://localhost:9200/exp09_five/_search" -H "Content-Type: application/json" -d '{"from": 10000, "size": 10, "sort": [{"no": "asc"}]}' | python -m json.tool
```

预期你会看到 400 报错（示意，节选；文案以实际为准）：

```json
{
  "error": {
    "root_cause": [
      {
        "type": "illegal_argument_exception",
        "reason": "Result window is too large, from + size must be less than or equal to: [10000] but was [10010]. See the scroll api for a more efficient way to request large data sets. This limit can be set by changing the [index.max_result_window] index level setting."
      }
    ],
    "type": "search_phase_execution_exception",
    "reason": "all shards failed"
  },
  "status": 400
}
```

注意报错里的关键数字：10000 和 10010——限制的是 `from + size` 的和，不是 from。验证一下边界，退一格刚好踩线：

```bash
curl -s -X POST "http://localhost:9200/exp09_five/_search?filter_path=took" -H "Content-Type: application/json" -d '{"from": 9990, "size": 10, "sort": [{"no": "asc"}]}'
```

```json
{"took": 43}
```

（示意）这个请求成功返回——`9990 + 10 = 10000`，恰好等于上限，放行。

### 第 2 步：深翻页的放大对比——1 分片 vs 5 分片

四条请求，只看 took。每条跑三五次再下判断（第一次请求偏慢是缓存和 JIT 的锅，看稳定后的值）：

```bash
curl -s -X POST "http://localhost:9200/exp09_one/_search?filter_path=took" -H "Content-Type: application/json" -d '{"from": 0, "size": 10, "sort": [{"no": "asc"}]}'
```

```bash
curl -s -X POST "http://localhost:9200/exp09_one/_search?filter_path=took" -H "Content-Type: application/json" -d '{"from": 9000, "size": 10, "sort": [{"no": "asc"}]}'
```

```bash
curl -s -X POST "http://localhost:9200/exp09_five/_search?filter_path=took" -H "Content-Type: application/json" -d '{"from": 0, "size": 10, "sort": [{"no": "asc"}]}'
```

```bash
curl -s -X POST "http://localhost:9200/exp09_five/_search?filter_path=took" -H "Content-Type: application/json" -d '{"from": 9000, "size": 10, "sort": [{"no": "asc"}]}'
```

预期你会看到（示意；绝对值随机器不同，相对关系应当复现）：

| 请求 | 1 分片 | 5 分片 |
|------|--------|--------|
| from=0, size=10 | ~3ms | ~9ms |
| from=9000, size=10 | ~18ms | ~47ms |

两个规律：**翻得越深越慢**（两个索引都是 from=9000 比 from=0 慢好几倍）；**分片越多，深翻页被放大得越狠**（1 分片从浅到深慢了 6 倍，5 分片慢了 5 倍还多，而且 5 分片的深翻页比 1 分片的深翻页又慢了一倍以上）。注意这是全部 5 个分片挤在同一台机器、同一个 JVM 里的成绩——没有一毫秒网络开销，慢的全是排序和归并本身。

### 第 4 步：脚本遍历全量 30 万

手动翻两页只是看清结构，真翻完 30 万条用脚本（[exp09-traverse.py](lab/scripts/exp09-traverse.py)）：

```bash
python scripts/exp09-traverse.py
```

核心循环长这样（节选，完整见 lab/scripts/exp09-traverse.py）：

```python
# exp09-traverse.py 节选：main 函数的循环体
    pit_id = ES.open_point_in_time(index=INDEX, keep_alive=KEEP_ALIVE)["id"]
    print(f"PIT 已建立：{pit_id[:24]}...（id 是 base64，很长，截断显示）")

    total = 0
    pages = 0
    last_sort = None
    t0 = time.perf_counter()

    while True:
        params = dict(
            index=INDEX,
            pit={"id": pit_id, "keep_alive": KEEP_ALIVE},
            size=PAGE_SIZE,
            sort=[{"no": "asc"}],
        )
        if last_sort is not None:
            params["search_after"] = last_sort
        resp = ES.search(**params)
        hits = resp["hits"]["hits"]
        if not hits:
            break
        total += len(hits)
        pages += 1
        last_sort = hits[-1]["sort"]
        if pages % 5 == 0:
            print(f"  第 {pages} 页，累计 {total} 条，游标 no={hits[-1]['_source']['no']}")
```

预期输出（示意，节选）：

```text
PIT 已建立：46ToAwMDaWR5FVTVhN2IzUGh...（id 是 base64，很长，截断显示）
  第 5 页，累计 50000 条，游标 no=49999
  第 10 页，累计 100000 条，游标 no=99999
  第 15 页，累计 150000 条，游标 no=149999
  第 20 页，累计 200000 条，游标 no=199999
  第 25 页，累计 250000 条，游标 no=249999
  第 30 页，累计 300000 条，游标 no=299999
遍历完成：30 页，共 300000 条，耗时 6.8s
PIT 已关闭
```

30 页 × 10000 条，一页不少一条不重。对比一下：from+size 翻到第 10 页就撞墙、翻第 901 页要 47ms，PIT + search_after 一口气翻完 30 万条，每页开销都和第一页一样。这就是两套翻页机制的数量级差异。

## 现象解释

把四步串回[专栏三·03](../专栏三-运行机制/03-查询执行流程.md)的两阶段。

**第 1、2 步的账在 query 阶段。**一次搜索发进 5 分片的索引，协调节点把查询广播给每个分片，每个分片在本地排序、取出前 `from + size` 条，只返回轻量结果（doc id、排序值）；协调节点归并 5 份局部榜单，确定最终的前 `size` 名，然后 fetch 阶段只给上榜的 10 条取 `_source`。问题出在"每个分片取前 `from + size` 条"：你要的是全局第 9001~9010 名，每个分片不知道全局名次，只能老老实实把自己的前 9010 名都交上来，等协调节点归并——**每个分片都白取了一堆再被扔掉**。from 越深，白取越多；分片越多，白取的份数越多。第 2 步 5 分片比 1 分片慢一倍以上，不是网络（都在一个 JVM 里），是 5×9010 对 1×9010 的排序与归并。

`max_result_window = 10000` 就是为这笔账兜底的：默认翻页只许到 10000 条，超过直接拒绝。它不是配额限制，是保护——不然一个 `from=100000` 的请求就能让协调节点在内存里归并几百万条。

**第 3、4 步是另一套机制。**`search_after` 换了个问法：不问"第 N 页是哪些"，问"排序值在 X 之后的下 10 条是哪些"。每个分片只需从 X 之后取 size 条，没有 from，也就没有白取——每页开销恒定，第 30 页和第 3 页一样便宜。而 PIT 把"从哪之后"这个问题锚定在一个冻结的数据视图上：打开 PIT 那一刻，每个分片用哪个 searcher、看哪些 segment，都被固定住了。翻页期间无论发生写入、refresh 还是 merge，你翻的都是打开 PIT 那一刻的世界——这就是"翻页一致性"的机制保证，30 万条一条不重一条不漏的来源。

顺带一句老方案：更早的深遍历用 scroll（快照游标），它给批处理设计，上下文开销大、不适合分页给用户看，8.x 官方主推 PIT + search_after。思路是同一家族：游标 + 快照。

## 常见坑点

- **撞墙就调大 `max_result_window`。**这是最常见的"解决报错"：改成 200000，报错没了，代价藏在后面——每个深页请求都要协调节点归并 `分片数 × (from+size)` 条，内存和延迟随页深线性涨，等于亲手拆掉保险丝。真要深遍历，换 search_after；要给用户分页，先问产品"第 800 页真的有人看吗"。
- **以为 from+size 慢是网络慢。**本实验 5 个分片全在一台机器上照样慢一倍——瓶颈在每分片的排序取数和协调节点的归并，是 CPU 和内存的账。加机器、升带宽都救不了深翻页，只有换机制能救。
- **search_after 不带 PIT。**search_after 只是把排序值当游标，自己不带快照语义。两次翻页之间任何写入、删除、refresh 都会改变"这个排序值之后还有谁"：落在未翻区间的新文档会不请自来（总数对不上），未翻的文档被删就永远漏掉，排序键不唯一时边界抖动直接重复。带上 PIT 才有"世界定格"的保证。
- **只按非唯一键排序就用 search_after。**游标必须能唯一定位上一页最后一条。生产排序都带一个唯一 tiebreaker（比如 `_id` 或自增字段），否则同一排序值的一堆文档在两页边界处会随机分家。
- **拿 `hits.total` 当精确总数。**默认 `track_total_hits` 截到 10000——30 万条的索引返回 `"value": 10000, "relation": "gte"`。要精确总数用 `_count` API。

## 进一步实验

**看 PIT 的快照语义。**开一个 PIT，然后写一条 PIT 打开之后才存在的新数据，让它可见后分别在"PIT 里"和"PIT 外"各搜一次：

```bash
curl -s -X POST "http://localhost:9200/exp09_five/_pit?keep_alive=3m"
```

（记下返回的 id）然后：

```bash
curl -s -X PUT "http://localhost:9200/exp09_five/_doc/300000" -H "Content-Type: application/json" -d '{"no": 300000, "text": "PIT 打开后新写入的记录"}'
```

```bash
curl -s -X POST "http://localhost:9200/exp09_five/_refresh"
```

不带 PIT 直接搜 `no` 为 300000 的文档，预期找得到；带着 PIT 搜，预期找不到——PIT 里看不到快照之后的新数据。这就是脚本遍历 30 页不重不漏的另一面：代价是遍历期间新数据对你不可见。批量导出正好要这个性质（数据集不能一边导一边变），实时读己之写要的是另一套（回头翻实验 04）。

**把 max_result_window 调大试试深页（看完改回来）。**

```bash
curl -s -X PUT "http://localhost:9200/exp09_five/_settings" -H "Content-Type: application/json" -d '{"index.max_result_window": 20000}'
```

然后 `from=19000&size=10` 的请求能过了，看一眼 took（预期比 from=9000 又明显更慢，示意）。看完改回 10000——这是实验环境，调着玩可以，记住你拆的是什么。

## 最后，总结

- from + size 的限制是 `from + size <= 10000`（`max_result_window`），超了直接 400；那是保护，不是配额。
- 深翻页的代价：每分片本地排序取前 `from + size` 条，协调节点归并 `分片数 × (from + size)` 条——翻第 N 页按全量名次付钱；分片数放大这笔账。
- search_after 用排序值当游标，每页开销恒定；PIT 把数据视图冻结在打开那一刻，翻页不重不漏，代价是快照之后的新数据不可见。
- 交给用户的分页用 from + size（浅）；导出、全量遍历用 PIT + search_after；scroll 是上一代方案，知道即可。
