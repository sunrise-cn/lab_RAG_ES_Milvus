# 10 三节点：选主与脑裂【进阶】

## 这个实验验证什么

一句话：**master 选举需要多数派（quorum）——三节点停一个，剩下两个照样凑出 2/3、重新选出 master，数据面照常读写；停两个只剩一个，它永远不会把自己选成 master，宁可拒绝服务也不给脑裂开门。**

机制依据是 [专栏三·04 集群与分布式](../专栏三-运行机制/04-集群与分布式.md)第五节"脑裂"和第六节"红色排查线"。正文里"宁可不可用，不给脑裂开门"这句话，这一篇我们亲手把它按在实验台上。

这是【进阶】实验，和主环境完全隔离：独立 compose 文件 `lab/es-cluster.yml`，三个 ES 8.11.4 节点各 512m 堆，端口 9210~9212，不挂数据卷（每次 up 都是全新集群，随便折腾）。**内存提醒：主环境（约 5~6GB）+ 三节点集群（约 2GB）同时跑需要 8G+ 内存，不够就先把主环境停掉**（在 `lab` 目录 `docker compose down`，本实验做完再 `up -d` 起回来）。

全程 docker + curl，没有 Python 脚本。

## 实验材料构建

```bash
cd lab
docker compose -f es-cluster.yml up -d
```

三个节点没有配 healthcheck，等半分钟左右再验证（三个容器一起起，集群引导要等它们互相发现）：

```bash
curl -s "http://localhost:9210/_cat/nodes?v&h=name,node.role,master"
```

预期你会看到（示意；IP 已省，master 的 `*` 落在哪个节点以实际为准）：

## 实验步骤

### 第 1 步：认清现任 master

```bash
curl -s "http://localhost:9210/_cat/master?v"
```

```text
id                     host       ip        node
8kIdLDLASs-yN0D5zXqVOw 172.19.0.2 172.19.0.2 es01
```

（示意；id 是节点的持久 uuid，截断显示。）记下这个 id 和节点名——下面要停掉它。引导期哪个节点当选是竞选结果，**不一定是 es01**：你的 master 是谁，下一步就停谁。节点名和容器名的对应关系：es01 → `cluster-es01`、es02 → `cluster-es02`、es03 → `cluster-es03`。

### 第 2 步：停掉 master，看重新选举

假设第 1 步的 master 是 es01：

```bash
docker stop cluster-es01
```

马上连着敲几次下面两条（up 箭头 + 回车，手速要快）：

```bash
curl -s "http://localhost:9211/_cat/master?v"
```

```bash
curl -s "http://localhost:9212/_cat/master?v"
```

预期你会看到两种状态先后出现（示意，节选；文案以实际为准）：

```json
{"error": {"root_cause": [{"type": "master_not_discovered_exception"}], "type": "master_not_discovered_exception"}, "status": 503}
```

```text
id                     host       ip        node
Bz3ZnfPFSu-yN0D5zXqVOw 172.19.0.3 172.19.0.3 es02
```

前几秒是 `master_not_discovered_exception`（503，集群没有 master），几秒后换成新 master 的信息——**id 换人了**。`docker stop` 发的是 SIGTERM，ES 会优雅退出、向集群道别，选举几乎立刻开始，所以窗口很短；如果想看更长的窗口，进一步实验里用 `docker kill`。

（打到 9210 的请求现在是 connection refused——容器停了端口就没了，不是集群的事。看集群，去活着的节点。）

选举完成后看集群和数据面：

```bash
curl -s "http://localhost:9211/_cluster/health?filter_path=status,number_of_nodes"
```

```json
{"status": "green", "number_of_nodes": 2}
```

```bash
curl -s -X POST "http://localhost:9211/exp10_repl/_doc/4" -H "Content-Type: application/json" -d '{"no": 4, "text": "master 换人之后写入的数据"}'
```

```json
{"result": "created", "_shards": {"total": 2, "successful": 1}}
```

（示意，节选。）写入照常成功——master 选举期间短暂冻结的是元数据操作，数据面（读写）在选完之后立刻恢复。`_shards` 里的 total 2 是"1 个主分片 + 1 个副本"的应答账目；如果副本还在恢复中，successful 可能只有 1，副本追上后就是 2——具体数字随分片状态，以实际为准。

```bash
curl -s "http://localhost:9211/_cat/shards/exp10_repl?v&h=index,shard,prirep,state,node"
```

这里分两种情况，取决于主分片原来在不在线。**如果原来的主分片正好在 es01 上**，你会看到 p 和 r 换位（示意）：

```text
index      shard prirep state   node
exp10_repl 0     p      STARTED es03
exp10_repl 0     r      STARTED es02
```

原来 es03 上的副本被新 master 提升成了主分片，es02（新 master 所在节点）上补了一个新副本——**副本提升成主分片，这个决策只有 master 能做**，这就是为什么主分片挂掉后写入要等选举完成。**如果原来的主分片本来就在 es02 或 es03 上**，这两行一个字都不会动——es01 的死活和它们无关。两种都值得看一眼。

### 第 3 步：再停一个，只剩独苗

再停掉两个幸存节点中的一个（比如 es02）：

```bash
docker stop cluster-es02
```

现在集群只剩 es03 一个节点。问它 master 是谁：

```bash
curl -s "http://localhost:9212/_cat/master?v"
```

预期：`master_not_discovered_exception`（503），**而且这次不管等多久都不会恢复**。一个节点活着、数据也在、请求也答——但它就是选不出 master。

集群状态和写入也试一遍：

```bash
curl -s "http://localhost:9212/_cluster/health?local=true"
```

（不带 `local=true` 的请求会因为没有 master 而失败或挂住；`local=true` 让它只报本节点视角，颜色取决于分片落在哪——red 或 yellow 都正常，以实际为准。）

```bash
curl -s -X POST "http://localhost:9212/exp10_repl/_doc/5" -H "Content-Type: application/json" -d '{"no": 5, "text": "独苗状态下尝试写入"}'
```

写入挂很久然后失败——具体异常跟分片位置有关（副本提升需要 master 决策、主分片不在线等情况报错各不相同，以实际为准）。读取同样看运气：要的分片在 es03 上还能答，不在就部分失败或整体失败。核心观察就一条：**这个节点永远不会自己把自己选成 master**。

### 第 4 步：救回来一个，quorum 回来了

```bash
docker start cluster-es02
```

等十几秒，再问：

```bash
curl -s "http://localhost:9212/_cat/master?v"
```

预期 master 又有了——2 个节点活 = 2/3 = 多数派，凑齐了，选举恢复。再把 es01 起回来，集群完整：

```bash
docker start cluster-es01
```

```bash
curl -s "http://localhost:9210/_cat/nodes?v&h=name,master"
```

预期三行、一个 `*`。同样的集群，停一个能活、停两个就冻结、救回一个又活了——多一个节点少一个节点，生死的分界线就是"2"这个多数派数字。

### 第 5 步：回主环境，看单节点的 yellow

三节点集群实验到此为止，先收掉（在 `lab` 目录）：

```bash
docker compose -f es-cluster.yml down
```

主环境如果刚才停了就起回来（`docker compose up -d`），然后回到熟悉的 9200。单节点上建一个同样"1 主 1 副"的索引：

```bash
curl -s -X PUT "http://localhost:9200/exp10_solo" -H "Content-Type: application/json" -d '{"settings": {"number_of_shards": 1, "number_of_replicas": 1}}'
```

```bash
curl -s -X POST "http://localhost:9200/exp10_solo/_doc/1" -H "Content-Type: application/json" -d '{"no": 1, "text": "单节点上的实验数据"}'
```

```bash
curl -s "http://localhost:9200/_cat/indices/exp10_solo?v&h=index,health,status,docs.count"
```

```text
index     health status docs.count
exp10_solo yellow open          1
```

**yellow**。写入成功、数据可查，但集群不 green。看分片：

```bash
curl -s "http://localhost:9200/_cat/shards/exp10_solo?v&h=index,shard,prirep,state,node"
```

```text
index      shard prirep state      node
exp10_solo 0     p      STARTED    es01
exp10_solo 0     r      UNASSIGNED
```

（示意）主分片 STARTED，副本 UNASSIGNED——整个集群只有一个节点，它想去哪？直接问 ES 本人为什么（专栏三·04 第六节的标准排查动作）：

```bash
curl -s -X GET "http://localhost:9200/_cluster/allocation/explain" -H "Content-Type: application/json" -d '{"index": "exp10_solo", "shard": 0, "primary": false}'
```

预期 explain 的结论大意是：这个副本分不出去，因为**同一个主分片的另一份拷贝已经在唯一的数据节点上了**——一个节点上放两份副本等于没放，副本的意义就是"另一台机器上再存一份"。

## 现象解释

三个实验场景对着 [专栏三·04](../专栏三-运行机制/04-集群与分布式.md)对号入座：

**为什么停一个节点能自愈？**多数派。3 个 master 候选的多数派是 2：停掉 master 后剩下两个节点，2/3 凑得出多数派，选举照常进行——第 2 步的短暂 503 之后 id 换人，就是这个过程。顺带看清楚了 master 的分工：选举期间冻结的是"户口本"操作（分片提升、元数据变更），数据面读写在新 master 选出后立刻恢复——控制面和数据面分离，master 不碰数据。

**为什么剩一个节点死活不选自己？**还是多数派。3 个候选的多数派是 2，一个节点只有 1 票，永远凑不出 2。它宁可对 `master_not_discovered` 503 到天荒地老，也不自己给自己投票。这一步是整个实验最重要的一眼：**如果没有这条规则**——每个少数派都自己选自己——网络把集群劈成两半时（A、B 一边，C、D、E 一边），两边各自称王、各自持有户口本、各自分配分片，分区愈合后两本户口本对不上，已确认的写入凭空消失。这就是脑裂。quorum 数学上封死了两个大脑：两个"超过半数"必然有交集，交集里的节点不会投两次票，所以同一时刻最多只有一个合法 master。**宁可不可用，不给脑裂开门**——第 3 步的拒绝服务是设计，不是故障。

**单节点为什么 yellow？**副本分配规则：同一个主分片的多份拷贝不能落在同一个节点（放两份在一台机器上，机器挂了一起没，等于没放）。单节点集群，主分片占了唯一的节点，副本无处安放——UNASSIGNED，yellow。yellow 的含义就是"数据都在，但兜底的副本缺失"。这也解释了为什么实验 09 的材料构建要显式把副本设为 0。

**那"两节点 + 一副本"是高可用吗？**不是，这是第 5 步埋的伏笔。两节点上建 1 副本的索引确实能 green（主分片和副本各占一个节点），看起来万事俱备。但两个 master 候选的多数派是 2——挂掉任何一个节点，剩 1/2 凑不出多数派，直接掉进第 3 步的冻结状态：数据都在，集群不干活。高可用要求的是"挂一个还能活"，quorum 的账决定它从 3 个节点起步。生产上的最小容错单元是三节点。

## 常见坑点

- **两节点 + 一副本就当高可用上线。**单副本索引在两节点上 green，看监控一切正常——直到某个节点重启，集群整体冻结（本实验第 3 步）。挂的不是数据是选票。三节点起。
- **实验做完忘了 down 三节点集群。**它常驻占 2GB 内存，主环境跑别的实验时会莫名吃紧。结尾的 `docker compose -f es-cluster.yml down` 别省。
- **两套 compose 搞混。**在 `lab` 目录里 `docker compose down` 停的是主环境；要停三节点集群必须带 `-f es-cluster.yml`。命令敲错方向，停错一套。
- **对着停掉的节点的端口 curl，以为集群坏了。**容器停了端口就没了，connection refused 只说明"这台机器不在"。看集群状态永远问活着的节点。
- **看到 `master_not_discovered_exception` 就当 bug 排查。**第 3 步它是设计行为。排查顺序：先数节点（quorum 够不够），再看日志。

## 进一步实验

- **拔电式宕机。**把第 2 步的 `docker stop` 换成 `docker kill`（SIGKILL，ES 来不及道别）。幸存节点要等故障检测超时（leader check，10 秒级）才确认 master 死了，选举窗口明显更长——生产上真正的机房断电、网络分区都是这种，优雅退出才是少数情况。
- **副本数的天花板。**在三节点集群上建一个 `number_of_replicas: 3` 的索引，看 `_cat/shards`：1 主 3 副本，节点只有 3 个，最多放下主分片 + 2 个副本，剩下 1 个副本 UNASSIGNED、索引 yellow——副本数受节点数限制，不是想写几写几。
- **重开一局。**`docker compose -f es-cluster.yml down` 再 `up -d`，看新集群引导期选出的 master 是不是还是同一个节点——引导期的竞选没有"资历"一说，谁快谁赢。

## 最后，总结

- master 候选的多数派规则：3 个候选要 2 票。停一个节点（2/3 在手）→ 重新选举、数据面恢复；停两个（1/3）→ 永久 503，宁可不干活不给脑裂开门。
- master 选举期间冻结的是元数据操作（副本提升、分片分配）；新 master 出来后数据面立刻恢复。主分片挂了要等选举，因为"提升哪个副本"只有 master 能拍板。
- 单节点上副本无处安放 → yellow；两节点单副本是假高可用——副本放得下，选票凑不齐。容错从三节点起步。
- 排查链：`_cat/nodes` 数节点 → `_cat/master` 认 master → `_cluster/health` 看颜色 → `_cluster/allocation/explain` 听解释。
