# 11 写入吞吐调优【进阶】

## 这个实验验证什么

一句话：**同样 30 万条数据，bulk 批大小（200/1000/5000/20000）× refresh 间隔（默认 1s / 关闭 -1）共 8 个组合，最差和最优差出一个数量级；关掉 refresh 换来的吞吐，代价是窗口期新数据不可搜——这是实验 04 那笔账的量级版。**

机制依据是 [专栏三·02 写入路径与近实时](../专栏三-运行机制/02-写入路径与近实时.md)：refresh 造 segment 的成本（第二步）、translog 默认每请求 fsync 所以"bulk 一次算一个请求、批得越狠 fsync 摊得越薄"（第三节）、批量导入的经典调优组合（第五节）。正文说"导入窗口该把 refresh 关掉"，这一篇我们量出"关掉到底值多少"。

这是【进阶】实验，但不用三节点集群，就在主环境单节点 ES（9200）上做，隔离靠索引：全部索引用 `exp11_` 前缀，做完统一删。

## 实验步骤

### 第 1 步：跑吞吐矩阵

```bash
python scripts/exp11-run.py
```

脚本（[exp11-run.py](lab/scripts/exp11-run.py)）先做一次预热（拿 5 万条把 JVM 和页缓存拉热，让 8 个组合在同一根起跑线上），然后按顺序跑 8 个组合——每个组合新建自己的索引（`exp11_b批数_模式`），把 30 万条灌进去，量导入耗时、算吞吐，最后手动 refresh 并核对 count。全跑完约 5~10 分钟，预期输出（**示意，节选——数值是按机制推理的量级，你的机器绝对值一定不同，看相对关系**）：

exp11_b200_roff       批   200  refresh -1  导入   34.9s  吞吐    8596 条/秒  末次 refresh   2.8s  count 300000 OK
exp11_b1000_roff      批  1000  refresh -1  导入   18.0s  吞吐   16667 条/秒  末次 refresh   3.1s  count 300000 OK

### 第 2 步：读表，三个规律

对着输出表看三条（示意数值下讲，你的数字比例可能略有出入，规律应该都在）：

1. **批越大越快，但边际递减。**refresh 1s 那四行：批从 200 加到 1000，吞吐翻倍；从 1000 到 5000，涨 40%；从 5000 到 20000，只剩 30%。请求开销被摊得差不多了，继续加批买不到更多。
2. **同样的批，关掉 refresh 明显提速。**批 200 一对比一下：85.3s 对 34.9s，2.4 倍（示意）。refresh 每 1 秒把 buffer 变成一个新 segment——导入 85 秒就是 80 多个段的"造段 + 开 searcher + 后台 merge 抢 IO"，这批账全免了。
3. **两个方向叠加最猛。**最差组合（小批 + 不关 refresh）对最优组合（大批 + 关 refresh）差出一个数量级——9.5 倍（示意）。这不是巧合，是设计出来的观察点：**批大小管请求开销，refresh 管造段开销，两者独立，乘起来就是数量级。**

还有一列"末次 refresh"值得单独看：roff 四个组合的导入结束后，脚本补的那次手动 refresh 各花了约 3 秒——**关掉 refresh 不是免了这笔账，是推迟了**。30 万条攒在 indexing buffer 里，最后一次造段全补上。摊到总账里依然大赚（导入快了 2~3 倍、补段 3 秒），但要记住这笔债存在。

exp11_b1000_r1s        300000            23     19.8mb
exp11_b5000_r1s        300000            11     19.2mb
exp11_b20000_r1s       300000             6     18.9mb

同样的数据，最差的组合留下几十个段，最好的只剩一两个——每次 refresh 造一个段，导入期 refresh 的次数直接写进了段数。段多的索引不只是磁盘碎：**每次查询要在所有段上各查一遍再归并**（实验 02、07 的账），导入爽完，查询买单。

### 第 4 步：代价验证——refresh 关着的时候，数据搜不到

吞吐的另一半代价。建一个 refresh 关闭的小索引，写三条，立刻搜：

```bash
curl -s -X PUT "http://localhost:9200/exp11_visible" -H "Content-Type: application/json" -d '{"settings": {"number_of_shards": 1, "number_of_replicas": 0, "refresh_interval": "-1"}, "mappings": {"properties": {"no": {"type": "long"}, "text": {"type": "text"}}}}'
```

```bash
curl -s -X POST "http://localhost:9200/_bulk" -H "Content-Type: application/json" --data-binary @- <<'EOF'
{"index": {"_index": "exp11_visible", "_id": "1"}}
{"no": 1, "text": "吞吐实验的可见性验证一"}
{"index": {"_index": "exp11_visible", "_id": "2"}}
{"no": 2, "text": "吞吐实验的可见性验证二"}
{"index": {"_index": "exp11_visible", "_id": "3"}}
{"no": 3, "text": "吞吐实验的可见性验证三"}
EOF
```

不等、不 refresh，直接搜：

```bash
curl -s -X POST "http://localhost:9200/exp11_visible/_search" -H "Content-Type: application/json" -d '{"query": {"match": {"text": "验证"}}}' | python -m json.tool
```

预期 `"total": 0`。但数据在不在？在——GET 立刻找得到（GET 走 translog，实时，这是实验 04 的结论）：

```bash
curl -s "http://localhost:9200/exp11_visible/_doc/1"
```

预期 `"found": true`。手动 refresh 一次，再搜，3 条全出来。这就是矩阵里 roff 四行的另一面：**导入期快出来的每一秒，都是用"这段窗口里数据不可搜"换的**。批量导入正好不在乎这个（导完再搜），线上持续写入的索引绝不能这么干。

## 现象解释

把 8 个组合的差距拆回[专栏三·02](../专栏三-运行机制/02-写入路径与近实时.md)的链路，两笔开销各自独立：

**笔一：每个请求的固定开销。**一次 bulk 不管装 200 条还是 20000 条，HTTP 解析、请求调度这些固定成本都要付一遍；更关键的是 translog 默认每个写请求返回前 fsync 一次（`request` 档）——**bulk 一次算一个请求**，所以批得越狠，fsync 摊得越薄。批 200 写 30 万条是 1500 次请求、1500 次 fsync；批 20000 只要 15 次。这就是批 200 到批 1000 吞吐翻倍的原因。批再往上加，固定成本已经摊没了，吞吐的增量就越来越小——20000 之后再加大，买不到什么，反而要开始付另一笔（见坑点）。

**笔二：refresh 的造段开销。**默认每 1 秒一次 refresh：把 indexing buffer 里的东西写成一个新的 segment——生成 FST、词表、posting list（实验 02 亲眼见过那套结构），打开 searcher，然后这个新段交给查询侧。导入期间每秒来一次，等于一边搬家一边办乔迁宴。关掉（-1）之后 buffer 只攒不吐，攒到最后手动一次性造段（所以末次 refresh 要 3 秒）。一个补充：`-1` 不是绝对零段——indexing buffer 默认上限是堆的 10%，堆 1g 就是约 100MB，攒满了照样强制 refresh，30 万条小文档大概率触发一两次，所以 roff 组合的段数是 1~2 不是必然的 1。

**为什么两个开关乘起来是数量级。**批大小决定"每条数据摊到多少固定成本"，refresh 决定"要不要边写边造段"，两者管的路不一样、互不替代，所以都调对才能拿到全部收益。生产上的导入组合（[专栏三·02](../专栏三-运行机制/02-写入路径与近实时.md)第五节）就是这么来的：**导入窗口内 refresh 关掉 + 副本置 0 + 批拉大，导完恢复设置、手动 refresh 还债**。副本置 0 这一步本实验单节点没法演示（本来就得是 0），副本对写入是同步放大，在实验 10 的三节点集群上可以自己加一步验证。

## 常见坑点

- **生产上直接抄 `-1` 忘了改回来。**导入组合只该活在导入窗口内。忘改回来的症状：写入全成功、监控全绿、搜索"丢"最新数据——第 4 步亲眼见过，`total: 0` 不是数据没了，是 refresh 没发生。导完恢复设置 + 手动 refresh，两步都不能省。
- **bulk 越大越好。**两个上限在前面等着：HTTP 层请求体默认上限 100MB，超了直接 413；更大的批意味着单请求占着更大的堆内存（服务端解析缓冲 + 客户端拼包），多客户端并发时一起压 GC。经验区间从"单请求 5~15MB 的数据量"起步，按机器和实测调，20000 条小文档（约 2MB）离上限很远，你的生产文档比这大得多，别按"条数"抄，按"请求体大小"估。
- **调优只看吞吐，不看段数和查询。**第 3 步那张表就是提醒：导入最快的组合留下 1 个段，最慢的留下几十个——但反过来看，如果这个索引导入完还要**持续写入**，1 个大段之后继续写，很快又从头攒段，还错过 merge 的自动回收。导入期组合适合"一次性灌完就查询"的场景，持续写入的索引要的是中间档（见进一步实验）。
- **拿实验数值直接定生产参数。**本实验的绝对吞吐只在这台机器、这个堆大小、这份数据上成立。矩阵给的是方向（批要大、导入期 refresh 要关），生产参数要用生产数据和生产机器压出来——这也是为什么把矩阵写成脚本：换数据重跑就是新的依据。

## 进一步实验

- **批拉到 50000 再跑一遍**（改 exp11-run.py 里的 `BATCH_SIZES`）。预期：和 20000 基本持平甚至略慢——固定成本摊无可摊，单请求堆压力先涨上去了。找到自己机器的"收益拐点"比记别人的数字有用。
- **refresh_interval 的中间档。**加一组 `"30s"`（REFRESH_MODES 里加一项，比如后缀 `r30s`）。预期：吞吐比 1s 明显好、比 -1 差，但可见性延迟从 1 秒变 30 秒——持续写入的索引在生产上更常选这档，吞吐和可见性之间的滑杆，不止两个端点。
- **副本的写入放大。**在三节点集群（实验 10）上把同一份 30 万条灌进 1 副本的索引，对比本实验的 0 副本吞吐——副本默认同步复制，站在写入关键路径上，预期吞吐再矮一截（示意即可，机制见[专栏三·04](../专栏三-运行机制/04-集群与分布式.md)第三节）。

## 最后，总结

- 批大小管请求开销（含每请求一次的 translog fsync），refresh 造段管写入期 IO；两个开关独立，调对一个翻一倍，两个都调对差一个数量级。
- 批不是越大越好：固定成本摊平之后收益归零，单请求内存和 100MB 上限在前面等着；按请求体大小估，不按条数抄。
- 关 refresh 的代价是可见性：窗口期新数据搜不到（GET 照样实时），导入结束手动 refresh 还债——实验 04 的结论在这里量出了价格。
- 生产导入组合：`-1` + 副本 0 + 大批量，导完恢复设置、手动 refresh，四步一个不能少。
