# 12 暴力与近似实测：自己画一条 recall-QPS 曲线

## 这个实验验证什么

FLAT 召回 100% 但 QPS 垫底；HNSW 和 IVF_FLAT 拿召回换速度。ef、nprobe 这两个旋钮各自能买回多少召回、又花掉多少延迟，文档说了不算，你自己量出来的曲线才算。这个实验用 10 万条带簇结构的向量，把 FLAT / HNSW / IVF_FLAT 的 recall@10 和 QPS 实测一遍，最后画成一条曲线。

关联正文：[专栏二·05](../专栏二-Milvus实战/05-索引与搜索参数.md)（调参方法论：拿 FLAT 当尺子、找拐点）、[专栏三·05](../专栏三-运行机制/05-ANN索引原理.md)（HNSW 的图和 IVF 的桶内部长什么样）。

## 实验材料构建

三个脚本，分工如下：

| 脚本 | 干什么 |
|------|--------|
| [exp12-gen.py](lab/scripts/exp12-gen.py) | 造 10 万条带簇结构的向量 + 100 条 query，建 collection exp12 |

| [exp12-plot.py](lab/scripts/exp12-plot.py) | 把测量结果画成 recall-QPS 曲线 |

先说数据怎么造，这里有个容易踩的坑：**别用纯随机向量**。真实 embedding 是聚团的——语义相近的文本在向量空间里挤在一起，用均匀随机向量测出来的 ANN 表现会失真偏乐观。所以材料脚本造一个"聚团的世界"：100 个簇心均匀撒在 [-1,1]^128 里，每条向量等于自己簇心加一份高斯噪声。噪声 sigma 取 0.35 也是挑过的：太小簇太干净，nprobe=1 都能接近满分召回，曲线失去动态范围；太大簇糊成一片，退化回均匀云。

还有个小设计：id 恰好等于 簇号*1000 + 簇内序号。后面看漏检时，光看 id 就知道漏的是不是隔壁簇的。

```python
# lab/scripts/exp12-gen.py
"""实验 12 材料：10 万条带簇结构的 128 维向量 + 100 条 query。

为什么不用纯随机：真实 embedding 是聚团的（语义相近的文本挤在一起），
纯均匀随机数据下 ANN 索引的表现会失真偏乐观。这里造一个"聚团"的世界：
100 个簇心均匀撒在 [-1,1]^128 里，每条向量 = 自己的簇心 + 高斯噪声（sigma=0.35）。
sigma 是挑过的：太小（比如 0.1）簇太干净，IVF nprobe=1 都能接近满分召回，
曲线失去动态范围；太大（0.5 以上）簇糊成一片，退化回均匀云。
"""
import time
from pathlib import Path

import numpy as np
from pymilvus import (
    Collection,
    CollectionSchema,
    DataType,
    FieldSchema,
    connections,
    utility,
)

LAB = Path(__file__).resolve().parent.parent
DATA = LAB / "data"

COLLECTION = "exp12"
DIM = 128
N_CLUSTERS = 100
PER_CLUSTER = 1000          # 100 簇 x 1000 条 = 10 万条
N_QUERIES = 100
NOISE = 0.35
BATCH = 5000


def main():
    DATA.mkdir(exist_ok=True)
    connections.connect(host="localhost", port="19530")

    rng = np.random.default_rng(1212)

    # 100 个簇心，均匀撒在 [-1, 1]^128
    centers = rng.uniform(-1.0, 1.0, size=(N_CLUSTERS, DIM))
    # 每条向量 = 自己的簇心 + 高斯噪声；id 恰好等于 簇号*1000 + 簇内序号
    noise = rng.normal(0.0, NOISE, size=(N_CLUSTERS * PER_CLUSTER, DIM))
    vectors = np.repeat(centers, PER_CLUSTER, axis=0) + noise
    ids = np.arange(N_CLUSTERS * PER_CLUSTER, dtype=np.int64)

    # query 从簇心加噪声采样：和库内向量同分布，但独立加噪
    q_center = rng.integers(0, N_CLUSTERS, size=N_QUERIES)
    queries = centers[q_center] + rng.normal(0.0, NOISE, size=(N_QUERIES, DIM))

    if utility.has_collection(COLLECTION):
        utility.drop_collection(COLLECTION)

    schema = CollectionSchema([
        FieldSchema("id", DataType.INT64, is_primary=True),
        FieldSchema("vector", DataType.FLOAT_VECTOR, dim=DIM),
    ])
    col = Collection(COLLECTION, schema)

    t0 = time.perf_counter()
    for i in range(0, len(ids), BATCH):
        col.insert([ids[i:i + BATCH].tolist(), vectors[i:i + BATCH].tolist()])
        print(f"insert {min(i + BATCH, len(ids))}/{len(ids)}")
    col.flush()
    print(f"insert+flush 耗时 {time.perf_counter() - t0:.1f}s，num_entities={col.num_entities}")

    np.savez(DATA / "exp12.npz", queries=queries)
    print(f"query 已存 {DATA / 'exp12.npz'}")
    print("材料就绪。下一步：python scripts/exp12-run.py")


if __name__ == "__main__":
    main()
```

然后是主测量脚本。注意它会反复拆掉 exp12 的索引重建（FLAT → HNSW → IVF_FLAT），所以重跑它之前先重跑一遍 gen，从干净状态开始：

```python
# lab/scripts/exp12-run.py
"""实验 12 主测量：FLAT 标尺 -> HNSW 扫 ef -> IVF_FLAT 扫 nprobe。

产物：lab/data/exp12-results.json（给 exp12-plot.py 画图）。
注意：这个脚本会把 exp12 的索引反复拆掉重建；重跑前建议先重跑 exp12-gen.py。
"""
import json
import time
from pathlib import Path

import numpy as np
from pymilvus import Collection, connections

LAB = Path(__file__).resolve().parent.parent
DATA = LAB / "data"

COLLECTION = "exp12"
TOPK = 10
WARMUP = 3

FLAT = {"index_type": "FLAT", "metric_type": "L2", "params": {}}
HNSW = {"index_type": "HNSW", "metric_type": "L2",
        "params": {"M": 16, "efConstruction": 200}}
IVF = {"index_type": "IVF_FLAT", "metric_type": "L2", "params": {"nlist": 100}}


def rebuild(col, index_params):
    """幂等地把索引换成 index_params，返回建索引耗时（秒）。"""
    try:
        col.release()          # 没 load 过就 release 会报错，吞掉
    except Exception:
        pass
    if col.has_index:
        col.drop_index()
    t0 = time.perf_counter()
    col.create_index(field_name="vector", index_params=index_params)
    build = time.perf_counter() - t0
    col.load()
    return build


def run_batch(col, queries, search_params):
    """逐条搜完全部 query，返回 (总耗时s, 平均单查ms, 每条命中的 id 列表)。"""
    for q in queries[:WARMUP]:                     # 热身 3 条，不计入
        col.search(data=[q.tolist()], anns_field="vector",
                   param=search_params, limit=TOPK)
    t0 = time.perf_counter()
    results = [col.search(data=[q.tolist()], anns_field="vector",
                          param=search_params, limit=TOPK) for q in queries]
    total = time.perf_counter() - t0
    id_lists = [list(hits.ids) for hits in results]
    return total, total / len(queries) * 1000, id_lists


def recall(id_lists, truth):
    hit = sum(len(set(a) & set(b)) for a, b in zip(id_lists, truth))
    return hit / (len(truth) * TOPK)


def main():
    connections.connect(host="localhost", port="19530")
    queries = np.load(DATA / "exp12.npz")["queries"]
    col = Collection(COLLECTION)
    results = {}

    # ---- 阶段 A：FLAT，暴力标尺，顺便产出 ground truth ----
    build = rebuild(col, FLAT)
    print(f"[A] FLAT 索引就绪（build {build:.1f}s）")
    total, avg, truth = run_batch(col, queries, {"metric_type": "L2", "params": {}})
    qps = len(queries) / total
    print(f"[A] 100 条 query：总耗时 {total:.2f}s，平均 {avg:.1f}ms/条，QPS {qps:.0f}")
    print(f"[A] recall@10 = {recall(truth, truth):.4f}（拿 FLAT 对 FLAT，定义就是 1）")
    results["flat"] = {"recall": 1.0, "qps": qps, "avg_ms": avg}

    # ---- 阶段 B：HNSW，扫 ef ----
    build = rebuild(col, HNSW)
    print(f"[B] HNSW 索引就绪（build {build:.1f}s，比 FLAT 慢一个量级）")
    results["hnsw"] = {}
    for ef in [8, 16, 32, 64, 128]:
        total, avg, id_lists = run_batch(
            col, queries, {"metric_type": "L2", "params": {"ef": ef}})
        r = recall(id_lists, truth)
        results["hnsw"][ef] = {"recall": r, "qps": len(queries) / total, "avg_ms": avg}
        print(f"[B] ef={ef:<3} recall@10={r:.4f}  avg={avg:.2f}ms  QPS={len(queries) / total:.0f}")

    # ---- 阶段 C：IVF_FLAT，扫 nprobe ----
    build = rebuild(col, IVF)
    print(f"[C] IVF_FLAT 索引就绪（build {build:.1f}s，含 k-means 训练；nlist=100 对应 100 个簇）")
    results["ivf"] = {}
    for nprobe in [1, 4, 16, 64]:
        total, avg, id_lists = run_batch(
            col, queries, {"metric_type": "L2", "params": {"nprobe": nprobe}})
        r = recall(id_lists, truth)
        results["ivf"][nprobe] = {"recall": r, "qps": len(queries) / total, "avg_ms": avg}
        print(f"[C] nprobe={nprobe:<2} recall@10={r:.4f}  avg={avg:.2f}ms  QPS={len(queries) / total:.0f}")

    with open(DATA / "exp12-results.json", "w", encoding="utf-8") as f:
        json.dump(results, f, ensure_ascii=False, indent=2)
    print(f"结果已存 {DATA / 'exp12-results.json'}，下一步：python scripts/exp12-plot.py")


if __name__ == "__main__":
    main()
```

```text

```

二十来秒是 HNSW 的入场费：每个点插入都得在图上先走一遍贪心才能找到自己的位置，建索引本身就是 10 万次搜索。对照 FLAT 的 build 0.1s——图结构的钱在建索引时就付掉了。机器不同这个数字差别很大，几秒到几十秒都正常。

**3. 扫 ef：同一个索引上拧五个档位**

ef 是搜索参数，不用重建索引，换档就是换个请求参数。脚本在 {8, 16, 32, 64, 128} 五档上各跑一轮，预期你会看到（示意，节选；绝对数字看机器，趋势才可复现）：

```text
[B] ef=16  recall@10=0.9093  avg=1.58ms  QPS=633
[B] ef=32  recall@10=0.9573  avg=2.05ms  QPS=488
[B] ef=64  recall@10=0.9803  avg=2.94ms  QPS=340
[B] ef=128 recall@10=0.9917  avg=4.71ms  QPS=212
```

整理成趋势：ef 每翻一倍，recall@10 向 100% 逼近一截，QPS 逐级下滑。ef=8 的单查延迟不到 FLAT 的四分之一，但召回只剩八成多；ef=128 时召回 99.2%，代价是 QPS 掉到 ef=8 的三分之一。

一个细节：ef=8 比 top-10 还小。ef 的下限是 top-k，Milvus 底层的 knowhere 会把过小的 ef 抬到 top-k（此行为待验证，以 pymilvus 2.4.4 / Milvus 2.4.4 实际行为为准），所以 ef=8 那一行实测的行为接近 ef=10。

脚本再把索引换成 IVF_FLAT，nlist 定 100——这是故意的：IVF 建索引时跑 k-means 聚出 100 个桶，而我们造数据时正好埋了 100 个簇，桶和数据本身的簇结构对上了。扫 nprobe 四档，预期你会看到（示意，节选）：

```text

[C] nprobe=1  recall@10=0.7410  avg=0.87ms  QPS=1149
[C] nprobe=4  recall@10=0.9033  avg=1.12ms  QPS=893
[C] nprobe=16 recall@10=0.9767  avg=2.31ms  QPS=433
[C] nprobe=64 recall@10=0.9953  avg=5.90ms  QPS=169
```

nprobe=1 只扫 query 最近的 1 个桶，QPS 冲到全场最高，但召回只剩七成多；nprobe=64 时召回 99.5%，QPS 却掉回 169——和 FLAT 的 163 一个档次了。扫 64/100 个桶，干的活已经和暴力检索差不多重，多花的钱没换来对等的收益。旋钮不是越大越好，拧过头就白烧延迟。

## 现象解释

FLAT 为什么慢：它没有任何结构，每条查询都和全库逐一算距离，算力和数据量成正比。10 万条时单查 6ms 还能忍，数据量涨它就线性恶化——进一步实验你会亲眼看到。

HNSW 为什么能又快又不太准：它把全库连成一张近邻图，查询从顶层入口进图、贪心地往 query 挪，每一步只看邻居，大部分向量根本没被碰过——这就是"抄近道"。**ef 控制搜索时候选队列的长度**，也就是探索广度：队列越长，越多"看起来次优"的候选被留在队里等翻盘，漏掉真近邻的概率越小，但要比的距离也越多。ef 从 8 到 128，你付的是延迟，买回来的是从 82% 到 99% 的召回。

IVF_FLAT 为什么 nprobe=1 时漏、nprobe=64 时亏：查询先和 100 个簇心算距离（很便宜），再进最近的 nprobe 个桶里暴力扫。nprobe=1 等于赌"真近邻都在最近的桶里"，桶边界上输掉的那部分就是召回损失；nprobe 逼近 nlist 时扫的范围逼近全库，又叠上簇心定位的开销，反而不如 FLAT 直接。

两个索引对照着看有个意外：这组数据偏向 IVF——簇结构干净、nlist 又恰好对上 100 个簇，IVF 在中档很能打，nprobe=16 用 2.3ms 换到 97.7% 召回，HNSW 同样花 2.1ms（ef=32）换到 95.7%。但这不是普适结论。真实 embedding 的边界比这糊，IVF 的桶划分质量一降，曲线整体往左下移，HNSW 的优势才拉开——所以正文把 HNSW 放在 RAG 的默认位置，同时反复强调别抄结论、自己量。IVF 常驻的优势在别处：建索引快（4 秒对 24 秒），内存不用背图结构。三角里没有白站的位置。

曲线怎么用：找拐点。召回增益明显放缓、QPS 还在掉的那个位置就是你的工作点。在这组示意数据上，ef=32~64 之间、nprobe=4~16 之间就是拐点区。这正是[专栏二·05](../专栏二-Milvus实战/05-索引与搜索参数.md)第六节那四步方法论（抽测试集 → FLAT 造标准答案 → 扫参数 → 找拐点）——你刚刚把它完整跑了一遍。

最后交代两个口径，免得数字被误读。其一，这里的 QPS 是单线程串行发 100 条 query 算出来的，约等于单查延迟的倒数，衡量延迟的相对关系够用，真要压吞吐得并发压测。其二，我们的数据是造得比较干净的 100 个簇，真实 embedding 的边界比这糊，IVF 在低 nprobe 档的表现现实里通常更差。

## 常见坑点

**只测延迟不测召回，等于白测。** 把 ef、nprobe 拧到最小档，延迟随便压，但检索质量已经没了。延迟和召回必须两列一起看，本实验的输出格式就是为这个设计的。最隐蔽的翻车姿势是：换了索引只看 QPS 变好了就上线，没人发现召回掉了 15%。

**测试 query 太少，结果不稳定。** 单条 query 的 recall 抖动很大（top-10 命中 9 条就是 0.9，差一条差一截），10 条 query 的均值还是飘的。100 条是底线，正文建议的 100~200 条就是这个原因。本实验固定用 100 条。

**recall@10 的分母是 ground truth 的 10 个最近邻，不是"返回结果里相关的比例"。** 前者是检索指标（和标准答案的交集除以 k），后者是相关性指标（需要人工或模型标注"相关不相关"）。两个都叫 recall，量的是不同维度的事，定义搞混了数字就没意义。本实验从头到尾用前者。

**抄别人的 ef=64 最佳配置。** 工作点绑定数据分布、维度、量级，别人的曲线不能替你做决定。把 exp12-run.py 改成你的真实数据，它就是你所有索引决策的尺子——这份脚本是资产，不是一次性实验。

## 进一步实验

把 exp12-gen.py 里的 PER_CLUSTER 从 1000 改成 5000（10 万条变 50 万条，id 编码不变），重跑 gen 和 run，看两件事：FLAT 的 QPS 掉到原来的五分之一左右（O(n) 线性恶化，每条查询要多算 40 万次距离）；HNSW 掉一点点（图搜索的路径长度是数据量的对数级）。两者的建索引耗时也各涨一截。这就是近似索引的可扩展性优势——数据量越大，用召回换速度这笔交易越划算。

顺带一提：50 万条时 nlist=100 已经不合适了（经验起点 4*sqrt(N)≈900），把 exp12-run.py 的 nlist 改成 900 再扫一轮 nprobe，看桶的划分质量对召回的影响。想看三角的另一条边——"用召回换内存"的量化压缩——留给进阶实验 16。

## 最后，总结

FLAT 是标尺：召回 100% 是定义不是成绩，代价是 O(n) 的每查询账单。HNSW 和 IVF_FLAT 的 ef、nprobe 都是"花延迟买召回"的旋钮，拧多大的依据不是抄配置，是拿固定测试集对 FLAT 量出来的 recall-QPS 曲线，找拐点定工作点。测试要 recall 和延迟两列一起看、100 条以上 query 起步、recall 的分母永远是标准答案的 top-k。这条曲线换数据就要重画——把你自己的验证脚本当资产养着。
