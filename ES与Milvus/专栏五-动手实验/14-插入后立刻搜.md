# 14 插入后立刻搜：一致性级别在等哪个水位

## 这个实验验证什么

insert 返回成功，不等于立刻搜索就能看到全部数据。能看到几条由**一致性级别**决定：Strong 每轮 100% 全见，是机制保证；默认级别和 Eventually 能见几条看时机，是概率。这个实验把三种级别各跑 10 轮，把"保证"和"概率"的差别亲眼看一遍，再去 attu 里看一眼 growing segment 的状态流转。

关联正文：[专栏三·06](../专栏三-运行机制/06-存算分离架构.md)（存算分离、timetick 水位、一致性级别机制）。

## 实验材料构建

| 脚本 | 干什么 |

gen 里有个容易忽略的顺序：**先建索引、load，再让 run 去 insert**。查询节点只对"已 load 的 collection"订阅增量流，growing segment 的可搜索性从这里来；顺序反了，看到的世界就不是这个实验要给你看的。

```python
# lab/scripts/exp14-gen.py
"""实验 14 材料：collection exp14 + 3500 条已知 id 的 128 维向量。

注意顺序：先建索引并 load，再让 run 去 insert。查询节点只对"已 load 的
collection"订阅增量流（growing segment），顺序反了看到的世界就不一样了。
"""
from pathlib import Path

import numpy as np
from pymilvus import (
    Collection,
    CollectionSchema,
    DataType,
    FieldSchema,
    connections,
    utility,
)

LAB = Path(__file__).resolve().parent.parent
DATA = LAB / "data"

COLLECTION = "exp14"
DIM = 128
N_ROWS = 3500      # 主实验用 3400（34 批 x 100），留 100 给 attu 环节


def main():
    DATA.mkdir(exist_ok=True)
    connections.connect(host="localhost", port="19530")

    rng = np.random.default_rng(1414)
    ids = np.arange(N_ROWS, dtype=np.int64)
    vectors = rng.normal(0.0, 1.0, size=(N_ROWS, DIM))

    if utility.has_collection(COLLECTION):
        utility.drop_collection(COLLECTION)
    schema = CollectionSchema([
        FieldSchema("id", DataType.INT64, is_primary=True),
        FieldSchema("vector", DataType.FLOAT_VECTOR, dim=DIM),
    ])
    col = Collection(COLLECTION, schema)
    col.create_index(field_name="vector", index_params={
        "index_type": "FLAT", "metric_type": "L2", "params": {}})
    col.load()

    np.savez(DATA / "exp14.npz", ids=ids, vectors=vectors)
    print(f"collection {COLLECTION} 已建好（FLAT 索引，已 load）")
    print(f"3500 条备弹已存 {DATA / 'exp14.npz'}")
    print("下一步：python scripts/exp14-run.py")


if __name__ == "__main__":
    main()
```

主测量脚本。核心手法：每轮插 100 条已知 id 的向量，insert 返回后**同一口气**里用 `id in [...]` 数这批 id 可见几条。同一个 collection 开三个句柄，就是三个不同一致性级别的"镜头"：

```python
# lab/scripts/exp14-run.py
"""实验 14 主测量：insert 之后立刻查，三种一致性级别各自能看到几条。

核心方法：同一批 100 条用已知 id 插入，insert 返回后"同一口气"里用
query 数这批 id 可见几条。Strong 是保证（每一轮都该是 100），
其他级别是概率（取决于查询节点追日志的时机）——这个实验的现象有时机性，
多跑几轮才作数。
"""
import time
from pathlib import Path

import numpy as np
from pymilvus import Collection, connections

LAB = Path(__file__).resolve().parent.parent
DATA = LAB / "data"

COLLECTION = "exp14"
BATCH = 100
ROUNDS = 10


def visible_count(col, ids):
    """立刻数这批 id 里可见几条，返回 (可见条数, 查询耗时 ms)。"""
    expr = "id in [" + ",".join(str(i) for i in ids) + "]"
    t0 = time.perf_counter()
    rows = col.query(expr=expr, output_fields=["id"])
    return len(rows), (time.perf_counter() - t0) * 1000


def main():
    connections.connect(host="localhost", port="19530")
    data = np.load(DATA / "exp14.npz")
    all_ids, all_vecs = data["ids"], data["vectors"]

    # 同一个 collection 的三个"一致性镜头"
    col_default = Collection(COLLECTION)                              # 服务端默认级别
    col_strong = Collection(COLLECTION, consistency_level="Strong")
    col_eventual = Collection(COLLECTION, consistency_level="Eventually")

    cursor = 0

    def take():
        nonlocal cursor
        ids = all_ids[cursor:cursor + BATCH]
        vecs = all_vecs[cursor:cursor + BATCH]
        cursor += BATCH
        return ids, vecs

    def round_once(col, label, verbose=True):
        ids, vecs = take()
        mr = col_default.insert([ids.tolist(), vecs.tolist()])
        n, ms = visible_count(col, ids)
        if verbose:
            print(f"[{label}] insert_count={mr.insert_count}"
                  f"  立刻可见 {n}/{BATCH}  查询耗时 {ms:.1f}ms")
        return n, ms

    print("== 第 1 步：默认一致性级别（insert 完立刻数）==")
    round_once(col_default, "默认")
    print("（单轮不作数，时机性现象，见文档）")

    print("== 第 2 步：Strong ==")
    round_once(col_strong, "Strong")

    print("== 第 3 步：Eventually ==")
    round_once(col_eventual, "Eventually")

    print("== 第 4 步：三种级别各 10 轮 ==")
    print(f"{'级别':<12}{'全见轮数':>8}{'平均可见':>10}{'平均查询耗时':>14}")
    for col, label in [(col_strong, "Strong"),
                       (col_default, "默认"),
                       (col_eventual, "Eventually")]:
        ns, mss = [], []
        for _ in range(ROUNDS):
            n, ms = round_once(col, label, verbose=False)
            ns.append(n)
            mss.append(ms)
        full = sum(1 for n in ns if n == BATCH)
        print(f"{label:<12}{full:>6}/10{np.mean(ns):>10.1f}{np.mean(mss):>12.1f}ms")

    print("\n下一步：python scripts/exp14-segment-demo.py（去 attu 看 growing segment）")


if __name__ == "__main__":
    main()
```

一个重跑约定：run 脚本每次都从 id=0 开始插，而 Milvus 的 insert **不查重主键**——重跑 run 而不重跑 gen，会插进一堆重复 id，"数这批 id 可见几条"就全乱了。重跑 run 前先重跑 gen。

默认              8/10      94.0        2.4ms

## 现象解释

先把 insert 返回成功那一刻发生了什么说清楚。proxy 把这 100 条写进 log broker、收到落盘确认，然后才给你返回 `insert_count=100`。此刻对象存储里还没有这批数据——你可以去 MinIO 控制台翻，翻不到。它的第一落点是日志，不是文件（这是[专栏三·06](../专栏三-运行机制/06-存算分离架构.md)写入路径的原样复刻）。

那查询节点凭什么能"立刻"搜到一部分？因为它对已 load 的 collection 订阅着同一条增量流，边收边攒进 growing segment，攒到的部分即刻可搜。传播本来就是毫秒级的，所以 insert 返回到 query 发出之间那几毫秒，多数时候够它消费完——这就是"默认级别也经常 100/100"的原因。看不到的部分，是消费进度还没追上。

一致性级别决定的就是查询**等不等这个进度**：Strong 把 GuaranteeTs 定在最新，查询节点必须确认自己消费追平了才执行；默认级别（Bounded，2.4 的默认值待验证，以 pymilvus 2.4.4 文档为准）允许落后一个容忍窗口；Eventually 完全不等。所以 Strong 的 100% 全见不是玄学，是"等到了才查"的直接结果；它慢出的那几毫秒，就是等水位的显性价格。

还有一个观察值得说：可见条数经常在 0 和 100 两个极端跳，中间值（比如 63/100）反而少。因为一轮 100 条是一个 insert 请求、一条日志消息，消费大体是整批的——要么整批到、要么整批没到。这个"整批性"你可以多跑几轮验证。

attu 里那个 Growing→Sealed 的变化是另一半故事：growing segment 要攒到大小上限（2.x 默认 512MB 量级，随版本调整）才自动封口，本实验总共才 1.8MB，只能靠闲置超时或手动 flush 封口。封口（seal）之后落对象存储成不可变的 sealed segment，这才是你在 MinIO 里能翻到的形态。第 5 步你亲眼把一个 growing segment 送到了 sealed。

## 常见坑点

**入库后拿"立刻搜索的条数"当写入成功断言。** 最常见的误判。写确认和读可见性是两件事：insert 的返回值已经确认了写入（数 insert_count 就够），可见性由一致性级别决定。用搜索条数当断言，数据明明写成功了，你却沿着"数据丢了"的方向排查，一错就是半天。

**和 ES 实验 04 的镜像关系要拎清。** [实验 04](04-写入后为什么查不到.md) 是 ES 的"写完搜不到"：GET 立刻可见、search 搜不到、1 秒后可见——那是 refresh 机制，**确定性现象**，只要落在 refresh 周期内必现。本实验是 Milvus 的"写完不一定全见"：大概率立刻全见、偶尔缺——**概率性现象**，取决于消费时机。机制也相反：ES 的增量可见要等"生成可搜索 segment"这个动作，Milvus 的增量可见靠追共享日志，天生快。镜像问题、相反概率——记住这对对比，比记住任何单个结论都值钱。

**一致性级别的场景分配。** RAG 知识库导入后的验收步骤（"确认 N 条全在库里"）用 Strong——这是少数必须保证全见的时刻；线上检索流量用默认级别就好，每次查询都等水位是白付延迟。正文还提过第三种：用户"上传即提问"的交互场景用 Session——自己写的东西自己马上能查到，比 Strong 便宜。

**重跑脚本插出重复 id。** Milvus 的 insert 不查重主键，重复 id 照插不误。重跑 run 前不重跑 gen，"数这批 id 可见几条"直接数乱，你会看到 100/100 变 200/200 这种灵异现象（id in 会命中两批同 id 的行）。

**Strong 没生效的排查。** 如果第 2 步 Strong 都跑出缺轮，先怀疑一致性级别没传到位：本脚本用的是"构造 Collection 时指定 consistency_level"的写法，pymilvus 2.4 也支持在 search/query 调用时按次传（两种传法以 pymilvus 2.4.4 实际行为为准）。级别没传上去，Strong 就退化成默认级别，缺轮自然重现。

## 进一步实验

flush 前后对比 Strong 搜索的耗时。做法：把 exp14-run.py 第 4 步抄一份改成"每轮 insert 之后先 col.flush() 再查"，跑 10 轮 Strong，和原版 Strong 的耗时对比。flush 强制把 growing segment 封口落盘、写路径上等的东西更多，代价更贵——Strong 是"读路径等水位"，flush 是"写路径强落盘"，两个价格标签都该认识一下。顺带看 flush 后 attu 里 segment 状态的即时变化。

## 最后，总结

insert 的返回确认的是"写进了日志"，不是"查询可见"；可见多少由一致性级别决定，级别的本质是查询前把消费进度追到哪个水位。Strong 是保证、默认和 Eventually 是概率，10 轮统计才能把两者分开；Strong 慢的那几毫秒就是等水位的价格。写成功与否看 insert_count，别拿立刻搜索的条数当断言。这个实验和 ES 实验 04 是一对镜像：一个是确定性的"没 refresh"，一个是概率性的"没等水位"——做过这两个，"写读可见性"这条线在两套系统里就都通了。
