# 15 标量过滤与分区裁剪：filter 到底是先过滤还是先搜索

## 这个实验验证什么

先摆一个直觉：往 search 里传 `filter='category == "cat_3"'`，你会自然把它理解成 SQL 的 WHERE——先把 category 是 cat_3 的行筛出来，再在这个子集里做向量检索。这个理解带出一个推论：只要满足条件的行够 k 条，top-k 就一定返回满 k 条。

这个实验第一件事，就是把这个推论放到一个只命中 0.1% 数据的 filter 下实测。你会看到它返回不满 k 条，而且换一个 query 条数就变。第二件事验证 partition key：同样的等值过滤，category 普通建法 vs 建成 partition key，两个 collection 各 50 轮搜索取平均延迟——后者让搜索"物理上不碰"其他分区的数据。

关联正文：[专栏二·03](../专栏二-Milvus实战/03-Collection与Schema.md)（partition 是检索裁剪工具，不是表大小管理工具）、[专栏二·06](../专栏二-Milvus实战/06-标量过滤与混合字段.md)（filter 表达式、bitset、pre/post-filter 的差别、partition key 的分工）。

## 实验材料构建

两个脚本，分工如下：

| 脚本 | 干什么 |
|------|--------|
| [exp15-gen.py](lab/scripts/exp15-gen.py) | 20 万条 128 维随机向量 + 10 个 category，灌进两个 collection：exp15-pk（category 是 partition key）、exp15-plain（普通标量字段） |
| [exp15-run.py](lab/scripts/exp15-run.py) | 三步测量：无 filter 基准 → 低选择率 filter → partition key 裁剪延迟对比 |

数据怎么设计。category 取 10 个值：cat_0~cat_8 九个常见值各 22,200 条，cat_rare 一个稀有值 200 条——20 万条里占 0.1%，它是步骤 2 的靶子。向量用均匀随机就够：这个实验量的是过滤行为，不是 ANN 召回，向量分布不影响结论。

对照实验的公平性靠一个细节保证：两个 collection 用同一个 rng 生成、同一批 insert，schema 里唯一的差别是 `is_partition_key` 一个参数。步骤 3 比延迟时，两边之间只有这一个变量。

```python
# lab/scripts/exp15-gen.py
"""实验 15 材料：同一份数据、两种 schema 的两个 collection。

exp15-pk   : category 建为 partition key（is_partition_key=True）
exp15-plain: category 是普通标量字段
两份数据逐行相同（同一个 rng 生成、同一批 insert），schema 里唯一差别是
is_partition_key 一个参数——步骤 3 的延迟对比里只有"分区裁剪"这一个变量。

数据：20 万条 128 维随机向量，10 个 category——cat_0~cat_8 各 22200 条，
cat_rare 200 条（选择率 0.1%，步骤 2 的靶子）。
向量用均匀随机：本实验量的是过滤行为不是 ANN 召回，分布不影响结论。
"""
import time
from pathlib import Path

import numpy as np
from pymilvus import (
    Collection,
    CollectionSchema,
    DataType,
    FieldSchema,
    connections,
    utility,
)

LAB = Path(__file__).resolve().parent.parent
DATA = LAB / "data"

DIM = 128
N_ROWS = 200_000
COMMON_EACH = 22_200          # 9 个常见值 x 22200 + cat_rare 200 = 200000
RARE = "cat_rare"
N_QUERIES = 50
BATCH = 5000
HNSW = {"index_type": "HNSW", "metric_type": "L2",
        "params": {"M": 16, "efConstruction": 200}}


def main():
    DATA.mkdir(exist_ok=True)
    connections.connect(host="localhost", port="19530")

    rng = np.random.default_rng(1515)
    vectors = rng.uniform(-1.0, 1.0, size=(N_ROWS, DIM))
    ids = np.arange(N_ROWS, dtype=np.int64)
    categories = np.array(
        [f"cat_{i}" for i in range(9) for _ in range(COMMON_EACH)] + [RARE] * 200)
    perm = rng.permutation(N_ROWS)          # 打乱：让 10 个值交错分布
    vectors, ids, categories = vectors[perm], ids[perm], categories[perm]

    for name, is_pk in [("exp15-pk", True), ("exp15-plain", False)]:
        if utility.has_collection(name):
            utility.drop_collection(name)
        schema = CollectionSchema([
            FieldSchema("id", DataType.INT64, is_primary=True),
            FieldSchema("vector", DataType.FLOAT_VECTOR, dim=DIM),
            # partition key：写入按 hash(category) 自动路由分区，等值过滤自动裁剪。
            # 分区数用服务端默认（2.4 的默认值待验证），不显式指定。
            FieldSchema("category", DataType.VARCHAR, max_length=32,
                        is_partition_key=is_pk),
        ])
        col = Collection(name, schema)
        t0 = time.perf_counter()
        for i in range(0, N_ROWS, BATCH):
            col.insert([ids[i:i + BATCH].tolist(),
                        vectors[i:i + BATCH].tolist(),
                        categories[i:i + BATCH].tolist()])
            if (i // BATCH) % 4 == 0:
                print(f"  {name} insert {min(i + BATCH, N_ROWS)}/{N_ROWS}")
        col.flush()
        col.create_index(field_name="vector", index_params=HNSW)
        col.load()
        print(f"{name}: {col.num_entities} 行，HNSW 索引，已 load"
              f"（灌数据 {time.perf_counter() - t0:.0f}s）")
        if is_pk:
            for p in col.partitions:
                print(f"  partition {p.name}: {p.num_entities} 行")

    queries = rng.uniform(-1.0, 1.0, size=(N_QUERIES, DIM))
    np.savez(DATA / "exp15.npz", queries=queries)
    print(f"query 已存 {DATA / 'exp15.npz'}")
    print("材料就绪。下一步：python scripts/exp15-run.py")


if __name__ == "__main__":
    main()
```

主测量脚本：

```python
# lab/scripts/exp15-run.py
"""实验 15 主测量：filter 的执行时机 + partition key 裁剪。

A. 无 filter 搜索：top-5 每次都满额（基准线）
B. 低选择率 filter（cat_rare，约 0.1%）：query() 拿得到全部 200 条，
   search() 却返回不满 5 条、跨 query 条数不稳定——"filter 织进 ANN 遍历"的现场
C. partition key 裁剪：cat_3（约 11%）等值过滤，plain vs pk 各 50 轮取均值
"""
import time
from pathlib import Path

import numpy as np
from pymilvus import Collection, connections

LAB = Path(__file__).resolve().parent.parent
DATA = LAB / "data"

PLAIN = "exp15-plain"
PK = "exp15-pk"
RARE = "cat_rare"
COMMON = "cat_3"
TOPK = 5
N_B = 10          # B：10 个不同 query 各搜一次
N_C = 50          # C：正式测量轮数
WARMUP = 5

# ef 不显式传，用默认（默认值多大待验证——B 段的"预算"就是它）
PARAM = {"metric_type": "L2", "params": {}}


def search(col, vec, expr):
    return col.search(data=[vec.tolist()], anns_field="vector",
                      param=PARAM, limit=TOPK, expr=expr)


def main():
    connections.connect(host="localhost", port="19530")
    queries = np.load(DATA / "exp15.npz")["queries"]
    plain, pk = Collection(PLAIN), Collection(PK)

    # ---- A. 基准：无 filter，top-5 满额 ----
    counts = [len(search(plain, q, "")) for q in queries]
    print(f"[A] 无 filter 搜 {len(queries)} 次，"
          f"返回条数 min={min(counts)} max={max(counts)}")

    # ---- B. 低选择率 filter：数据在库里，search 给不满 ----
    rare_expr = f'category == "{RARE}"'
    rows = plain.query(expr=rare_expr, output_fields=["id"])
    print(f"[B] 库内满足 {rare_expr} 的行数：{len(rows)}"
          f"（选择率 {len(rows) / plain.num_entities:.2%}）")
    per_query = [len(search(plain, q, rare_expr)) for q in queries[:N_B]]
    same_q = [len(search(plain, queries[0], rare_expr)) for _ in range(3)]
    print(f"[B] {N_B} 个不同 query 各搜一次，返回条数：{per_query}")
    print(f"[B] 同一个 query 连搜 3 次，返回条数：{same_q}")

    # ---- C. partition key 裁剪：同过滤，plain vs pk，多轮取均值 ----
    common_expr = f'category == "{COMMON}"'
    vec = queries[0]
    for name, col in [(PLAIN, plain), (PK, pk)]:
        for _ in range(WARMUP):
            search(col, vec, common_expr)
        ts = []
        for _ in range(N_C):
            t0 = time.perf_counter()
            hits = search(col, vec, common_expr)
            ts.append((time.perf_counter() - t0) * 1000)
        ts.sort()
        mean = sum(ts) / len(ts)
        print(f"[C] {name:<12} {common_expr}：均值 {mean:.2f}ms  "
              f"最小 {ts[0]:.2f}ms  中位 {ts[len(ts) // 2]:.2f}ms  "
              f"返回 {len(hits)} 条")


if __name__ == "__main__":
    main()
```

## 实验步骤

**1. 无 filter 基准：top-5 满额**

```bash
python scripts/exp15-run.py
```

先看 A 段，预期你会看到：

```text
[A] 无 filter 搜 50 次，返回条数 min=5 max=5
```

50 个 query、每个 top-5，全部返回 5 条。基准线画在这。

**2. 低选择率 filter：数据在库里，search 却给不满**

接着看 B 段。注意脚本先 query 后 search——query() 是纯标量取数的入口（相当于 SELECT），search() 才是向量检索。预期你会看到（示意；条数具体是几不重要，"不满且跨 query 不稳定"才是重点）：

```text
[B] 库内满足 category == "cat_rare" 的行数：200（选择率 0.10%）
[B] 10 个不同 query 各搜一次，返回条数：[3, 1, 4, 0, 2, 1, 3, 2, 0, 4]
[B] 同一个 query 连搜 3 次，返回条数：[3, 3, 3]
```

三行放一起看：满足条件的行有 200 条，是 top-5 的 40 倍，query() 一把全拿得回来；换成 search() 带 filter，返回 0~4 条不等。换一个 query 条数就变；同一个 query 连搜三次条数不变——ANN 在图上的行走路径由 query 决定，路径定了，预算内能撞见几条匹配的行也就定了。

如果你的版本实测总是返回满 5 条，先确认两件事：filter 选择率是不是真的 0.1%（看 B 段第一行）、索引是不是 HNSW（FLAT 是全量比对，不会缺额）。都确认过还是满额，就记下这个差异去啃现象解释——2.4 的过滤行为随小版本有调整，实测结果本身就是信息。

**3. partition key 裁剪：多轮取均值的延迟对比**

C 段换 cat_3——22,200 条、选择率 11.1% 的常见值。选择率够高，两个 collection 都稳定返回 5 条，延迟才有可比性。同一个 query，plain 和 pk 各热身 5 轮、正式测 50 轮，预期你会看到（示意；绝对数字看机器，相对关系才可复现）：

```text
[C] exp15-plain  category == "cat_3"：均值 3.62ms  最小 3.10ms  中位 3.55ms  返回 5 条
[C] exp15-pk      category == "cat_3"：均值 1.74ms  最小 1.42ms  中位 1.70ms  返回 5 条
```

两条延迟差几毫秒，或者差十几毫秒，都不重要——重要的是方向稳定：pk 比 plain 快。差值毫秒级，单轮对比毫无意义（下一轮网络一抖就盖过去了），所以脚本才做成 50 轮取均值。这个实验解释的重心在机制，不在数字大小。

## 现象解释

**步骤 2 的核心：filter 不是"先过滤再搜"。** 我们把三个心智模型摆开。模型一，pre-filter：先把 200 条 cat_rare 筛出来，在这个子集里做向量检索——预测返回满 5 条（子集里有 200 条，绰绰有余）。模型二，post-filter：先在全库做 ANN 检索拿 top-k 候选，再在候选里过滤——预测返回条数不足 5 且不稳定（候选里恰好有几条匹配就返回几条）。实测的现象符合模型二。

但 Milvus 的真实实现比模型二精细，介于两者之间。[专栏二·06](../专栏二-Milvus实战/06-标量过滤与混合字段.md)讲过：表达式先编译成一个 **bitset**（一行一个 bit，1 表示允许参与检索），搜索时带着 bitset 走 HNSW 的图遍历——被滤掉的点不能成为**结果**，但可以作为**路径**被路过，图不会断。所以准确的心智模型是第三个：**边搜边滤，预算定上限**。遍历的探索广度由 ef 决定（我们没显式传，走默认值，默认值是 2.4 的实现细节），遍历在预算内进行，预算用尽就停，找到几条算几条。选择率 11% 时，预算内大概率撞得满 5 条（C 段两边都是 5 条）；选择率 0.1% 时，预算内平均只能撞见零点几条匹配行——于是返回 0~4 条。

补一条解法：Milvus 2.4 提供了迭代式的搜索接口（pymilvus 的 search_iterator，凑不满 k 时继续翻页找），以及搜索参数里控制"边搜边滤"预算的旋钮，具体参数名和默认行为随小版本在动——待验证，以你手上版本的官方文档为准。

**步骤 3 的核心：partition key 是物理裁剪，filter 是逐行检查。** plain collection 带 cat_3 过滤，引擎要在 20 万行上求值表达式拿到 bitset，然后带着 bitset 在 20 万条向量的图上遍历。pk collection 里，写入时每行按 hash(category) 落进固定分区，等值过滤时引擎算出目标分区，其余分区的数据**整块不碰**——要建 bitset 的行少了九成，要在图上遍历的向量也少了九成。两处省下来的叠加，就是均值里那几毫秒。正文那句"filter 是检索时逐行检查，partition 是物理上根本不碰"，现在你有了自己的数字。

为什么 gen 脚本最后要打印分区行数：哈希分桶不保证一个值独占一个分区（10 个值可能撞车），但这不影响结论——裁剪掉的是"目标分区之外的所有分区"，撞车只影响剩下那一小块里还混着多少别的值。

## 常见坑点

**以为 filter 是"先过滤再搜"，所以必然返回满 k 条。** 步骤 2 整个就是它的反例。生产上这个坑的典型翻法：权限过滤（某租户只占全库 0.5%）+ top-10，上线才发现用户偶尔只搜回两三条，还以为是网络问题。低选择率的等值条件，解法不是加大 k，是把条件交给 partition key。

**拿"加大 top-k"硬扛。** 搜 top=500 再过滤？又慢又没保证——选择率 0.1% 时 500 个候选里期望也就撞见 0.5 条匹配。这条思路在[专栏二·06](../专栏二-Milvus实战/06-标量过滤与混合字段.md)第一节被批过一次（"k 越大越安全，也越慢，走到头就是暴力搜索"），这里亲手撞上了。

**partition key 只在等值过滤时才裁剪。** `category == "cat_3"` 裁剪，`category != "cat_3"`、范围比较、`in ["cat_3", "cat_4"]` 这类表达式不触发分区裁剪（in 是否对多值各自裁剪待验证）。选 partition key 字段的判据：每条查询必带、取值互斥的条件（租户、环境）才配得上它。

**filter 表达式的引号。** 表达式里的字符串字面量要带双引号，外面用单引号包整个表达式：`'category == "cat_3"'`。写成 `category == cat_3` 会报解析错误。

**对照实验不留神控制变量。** 步骤 3 如果两个 collection 的数据、索引参数、搜索参数有任何一处不同，延迟差就说不清来源。gen 脚本里"同一份数据灌两个 collection"的设计就是为这个。

## 进一步实验

把 exp15-run.py 里的 PARAM 改成 `{"metric_type": "L2", "params": {"ef": 128}}`，重跑 B 段——预算放大 8 倍（假设默认 ef 是 16），返回条数应该明显变多（多数 query 能到 4~5 条）。ef 就是"预算定上限"里那个预算，这一步等于亲手拧它。再调到 ef=512 看延迟涨多少——你会重新体会实验 12 的结论：旋钮拧过头，就是拿延迟白换。

或者改 gen 脚本，把 cat_rare 从 200 条加到 2000 条（选择率 1%），重跑全流程，找"开始稳定满额"的临界选择率。这个临界点和 ef、数据分布都有关，你的数字只对你的场景负责——所以它值得自己量。

## 最后，总结

filter 在 Milvus 里不是 SQL 的 WHERE：表达式编译成 bitset 织进 ANN 遍历，被滤掉的点不能当结果但能当路径，遍历预算用尽就停——选择率低时返回不满 k 条是这套机制的必然产物，不是 bug。低选择率、每查询必带的等值条件，交给 partition key：哈希分桶 + 等值裁剪，让其他分区的数据物理上不进比对范围。量这种毫秒级的差异，多轮取均值是底线；解释时把重心放在机制上，数字只是机制的回声。
